# 原始需求材料 → 需求条目

**什么时候用这一节**：输入不是成型的 PRD/原型，而是原始材料——需求表、Word 需求说明、版本划分表、客户口头补充。
输入已经是成型 PRD 的（有原型、有逐页规格），**跳过本节**，直接进现状核对。

**产物叫「需求条目表」**——一份独立文件，与设计文档并列，是后续设计的输入。头部跟其它产物一样固定记三个指纹：源材料的 sha256 · 代码仓库 commit · 上一轮产物路径。

产出的未决项**并进未决台账**（状态 `待外部需求方答复`），不另起一份文件。

---

## 一、需求条目

每条形状固定：

```
| 编号 | 功能（来源 · 出处） | 关键字段 / 规则 | 例子 | 分期 |
```

### 编号

格式 `前缀-序号`，如 `MBR-42`。前缀按端或模块划分，三到四个字母。

- **先找现有需求文档的前缀表**：有就沿用，序号接着该前缀的最大值往下编，**不另起一套**
- 没有就建一张，写进需求文档第一节，此后不再改
- 序号在前缀内递增，**删除条目不回收序号**
- 落不进任何前缀的条目，进未决台账问归属，**不新造前缀**

编号是跨文档引用的锚点——排期表、提测单、缺陷单、执行手册都靠它对上。**每换一套编法，等于这些引用全部断链。**

### 来源标签：每条带且只带一个

| 标签 | 含义 | 必须附带 |
|---|---|---|
| `【源】` | 源需求原文，逐字可引 | 出处（文档简称 + 行号/章节，或 `route#段名[下标]`） |
| `【例】` | 源文档里的**样例值**，是举例不是规格 | 原样例值 |
| `【定】` | 已定版：架构决策 / 会议纪要 / 项目硬约束 | 依据编号 |
| `【设】` | 源需求未写、我方补的实现预设 | 未决台账编号，如 `【设·⚠️A-12】` |

**`【设】` 与台账编号成对出现**：正文写 `⚠️A-12`，台账里必有 `A-12`；反向亦然。**两边编号集合必须相等**，产出后核一遍（校验脚本会查）。

**转述 ≠ 原文**：拿不到源件时标注「转述，未核对原文」，不用下游文档的转述冒充 `【源】`。找不到出处时说「未找到出处」，**不说「需求没说」**。

### 详细程度

| 范围 | 写到 |
|---|---|
| 在建期 | 页面与操作级——字段清单、按钮、状态流转 |
| 远期 | 功能级 + 只写**会影响在建期数据模型**的规则 |

源文档某一期写得特别细，说明的是那段的作者，不是它的优先级。**详细程度按上表定，不跟随源文档。**

## 二、取证纪律

- **用原件取证，不读有损导出**。中间格式的导出常常丢掉前置判定、状态机、种子数据，一律不回读
- **对基线**：分析或重检前先确认文档写作时的源文档版本差，有差就先读变更记录对应卷，列出会命中本模块的变更
- **对账**：`git diff <写作基线>..HEAD` 看该模块有没有变。⚠️ **页面文本零改动 ≠ 条目不用改**——横切规则（权限模型、数据范围、列表通用行为、状态机）常常只落在调整记录和运行时代码里，页面规格文本不跟着改。所以对账 = 本模块的 diff **加上** 版本差内变更记录逐条扫「涉及页面/接口」列
- **补缺口**：发现漏掉的页面/接口，补成条目

## 三、自洽检查

逐页比对规则、边界、数据、浮层、列表列，发现不自洽给「建议默认」+ 对应台账编号。

**什么进未决台账**：

- 源文档之间打架 → C 组（需求方自己对齐）。**有已定版决策能收口的，写进正文的「源文档冲突与已定版结论」表，不进台账**
- 源需求空白，且不同取值会改变数据模型或工期 → A / B 组
- 源文档自称「暂定 / 未想清楚」→ 必须收口，进 A 组；同时命中"产品没想清楚"信号的，走 🟣 候补路线（见 `deferral.md`）
- **客户写进本期清单、我方想砍掉的功能** → B 组，「谁答」写客户或业务

候补五要素见 `deferral.md` 第四节，A/B/C 分组见第六节。

---

## 四、范围削减

拆完做产能对账。超载时，削减权按来源标签分：

- `【设】` / `【定】` 条目 —— **我方自行决定**
- `【源】` 条目 —— **客户白纸黑字写进本期清单的功能，其削减进未决台账交需求方决定**，不在内部方案里直接划掉

---

## 五、不重复的内容

架构决策、模块边界、技术选型各有归属文档。需求条目**引用它们的编号，不复述内容**。
