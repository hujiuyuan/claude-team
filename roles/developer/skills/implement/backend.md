# 后端习惯（写服务端代码时读）

个人习惯与工程纪律，跨项目通用。技术栈、表名、目录结构、业务规则以项目自身的 CLAUDE.md 与文档为准，冲突时项目优先。

## 分清「已定的习惯」与「该论证的判断题」

回答任何设计问题前，先把分歧归到两类里，**两类的处理方式完全相反**：

- **A 类 · 代码习惯** —— 已经定了。**照做，不用重新论证，也不要在回答里旧事重提**
  （比如金额怎么存、主键怎么生成、文案能不能硬编码）。
- **B 类 · 架构判断题** —— **不是禁区**。有明确的判定依据就**对着依据论证**，
  不要拿通用最佳实践套，**也不要因为「现状是 X」就拒绝讨论**。

B 类的正确姿势，以「要不要拆微服务」为例：

- 不要直接答「我们是单体所以不拆」。**对着退出信号逐条核**，说清现在命中哪条、没命中哪条、
  要看什么指标才能判断。命中了就直说该拆。
- 反过来，**一条都没命中时要明确拒绝**，并说清是哪几条没命中，不要含糊其辞。
- 你在讨论别的事时观察到某条信号**已经出现**（设计里冒出跨模块分布式事务、某表查询量级明显失衡）
  → **主动提出来**，那正是该说话的时候。
- 「一期不做」意味着一期内不做，**不意味着不能分析**。

同理适用于 K8s / Serverless / 多云 / CQRS / Event Sourcing：不在范围内不等于不能谈，
但要说清「它解决的问题是什么、当前方案哪里不够、代价是什么」，而不是「最佳实践建议采用」。

## 技术栈：读，不要猜

**动手前先读项目的 `CLAUDE.md` / README / 构建文件确认实际用的是什么。**

不要凭「这类项目多半用某某 ORM」「多半用某某构建工具」这类生态常识推断。同一个语言同一个框架，
持久层、构建工具、边界守卫的选型都可能与常见组合不同。**猜错技术栈的代价是整轮工作方向错误**，
而这类错误往往到跑测试时才暴露。

## 拿到 PRD 后的功能设计拆分

**目的**：把 PRD（业务需求）拆成可落地、可估时、可验收的功能点，前后端对齐接口契约后再动手写代码。产出是一份功能设计，每个功能点都有固定落点，不靠临场发挥。

### 拆分颗粒度

一个「功能点」必须同时满足三点，缺一不可：

- **能独立交付**——不依赖另一个功能点先做完才能写
- **能独立验收**——有一条明确的「做完长什么样」的判定
- **能独立估时**——能说清它要做几步、做多久

太大拆不动（一个点里藏三个需求，验收时扯不清），太小碎成渣（一次提交改八个文件却说不出做了啥）。

### 前端拆分：四个维度，逐层问

每页/每块功能拆到四层：

1. **整体页面 UI 展示**——这页长什么样、有哪些区块、区块间主次与交互
2. **子模块分布**——每个区块拆成哪些子组件、各自职责
3. **是否通用模块**——这个组件/区块在别处还用吗？判定见下「通用模块与工具类」
4. **关联字段展示整理**——每个展示字段从哪来、怎么展示（脱敏 / 字典翻译 / 格式化 / 关联实体）

**第 4 层必须联合后端一起定**——展示形态取决于后端出参结构。前端想要的「关联展示」与后端能给的「出参结构」不一致时，要在设计阶段对齐，而不是前端先按想象画、后端再返工。

### 后端拆分：四件事，每个功能点都落到

1. **接口设计**——method / path / 入参 / 出参 / 权限 / 错误码。入参出参就是前后端契约
2. **表设计**——涉及哪些表：新增 / 改字段 / 加索引。改表前回项目建表规范（主键、外键、唯一约束）
3. **通用工具类抽象**——哪些复用点该抽成工具类，判据见下
4. **复杂逻辑 / 复杂调用画图**——边界见下

### 通用模块与工具类：判据是「第二次出现」，不是「看起来像」

「是否通用」最容易被**预判抽象**带偏——看见两个页面都列了个表格就抽「通用表格组件」，抽完发现第三个场景表格要分页、第四个要树形，通用件越改越胖，反而拖累私有场景。

判据分两类，别混：

- **项目基建**（UUID、脱敏、审计、异常、i18n 这类）：开工前就定，属于「已定习惯」，不是判断题
- **业务复用组件/工具类**：**第二次出现的真实场景**才抽。第一次出现先按私有写死；第二次出现时先看两处是否真的同构——结构、字段、行为都一致才抽，不一致就各自留着，不硬凑

判据一句话：**「这个抽象能在第二个场景原样用上吗？」想不出那个具体场景，就别抽。**

### 流程图与时序图的边界：不是「复杂」两个字能当判据

「复杂逻辑画流程图、复杂调用画时序图」这句话本身没有可执行性——什么叫复杂，两个人答案不同。落成可判定边界：

- **画流程图**：单一功能**内部**逻辑分叉多时——状态机、审批链、多条件判定、有顺序依赖的规则。画它是因为这些分支若散在代码里，会各写各的、对不上。简单 CRUD 不画
- **画时序图**：一次动作**牵动多模块 / 跨系统**时——跨多个 owner service、跨事务边界、调第三方、有异步/回调。画它是为了明确调用顺序、事务边界、失败回滚点。单 service 内部自洽不画

### 前后端联动的关键产出：关联字段清单

「关联字段展示整理」落到纸面就是一张清单，每行一个字段：

| 字段 | 来源表 | 来源字段 | 是否脱敏 | 是否字典翻译 | 展示格式 | 是否可编辑 |

这张表是前后端对契约的**唯一凭据**——后端按它定出参、前端按它定渲染，谁改一边都能从这张表看出另一边要不要跟着动。

## 数据库与 Schema 习惯

### 主键列名用 `<表实体单数名>_id`，不是 `id`

例如 `order.order_id`、`customer.customer_id`。理由：外键列名与被引列名同名，JOIN 条件自解释；
`a.id` / `b.id` 在多表 JOIN 里读不出是谁的。技术主键与业务编号分离这条不变。

### 多对多关联表统一用后缀 `_rel`

`<实体A>_<实体B>_rel`，主键随之是 `<实体A>_<实体B>_rel_id`。

用后缀不用前缀：按实体名排序才是日常查表的方式，同一实体的表能连成一片
（`order` / `order_item` / `order_coupon_rel` / `order_payment`）；前缀会把它们打散，
而且主键会变成 `rel_order_coupon_id`，前缀跑到实体名前面，与 `<实体>_id` 的规则读起来相斥。

**若表内已有叫 `rel` 的列，把列名展开成 `relation`**——后缀是缩写、列名是全词，
一眼分得清哪个是表哪个是列，避免 `xxx_rel.rel` 结巴。

**不要为了躲结巴就改叫 `role`**：`角色` 在很多业务里已经是 RBAC 的专有词（挂在账号上），
而 `身份` 往往又是另一个专有词（挂在自然人上）。一张关联表的关系列多半两个都不是——
它描述的是「这两个实体之间是什么关系」。**换列名前先 grep 一遍那个词在本项目有没有主人**，
借一个已被占用的词造成的歧义，比原本那点结巴严重得多。

**关联表带自己的属性时同样适用**：很多关联表不是纯连接，会带业务编号、生效/失效时间、
角色等等。带属性不改变它是关联表这个事实，照样加 `_rel`。

### 派生状态不落库

会随时间自动变化的值（状态名、是否过期、是否仍在有效期内）一律**渲染时算**，不存。
存一份必然过期。任何地方要判断当前状态，问那个唯一的判定实现，**不许直接读原始列**。

同一份业务规则若不得不有第二份实现（比如为了能在 SQL 里分页筛选而重写一遍），
**必须配一致性测试证明两份等价**，并提供一个故意写坏的版本证明该测试会红。

### 枚举的字符串还原：写入严格，展示宽松

严格版认不出直接抛异常，只用于**写入**路径；展示路径一律用宽松版返回 null。
理由：列上通常没有 DB CHECK 兜底，一个脏值会让**整页列表 500**，同页正常记录跟着遭殃。

### 主键用 UUIDv7，应用侧生成，DDL 不写 DEFAULT

不要 `DEFAULT gen_random_uuid()`——那是随机 v4，时间无序，B-tree 页分裂率高。
UUIDv7 前缀有时间序，插入局部性接近自增。**应用侧生成**还有个硬理由：多表事务需要在
`INSERT` 之前就持有各聚合的 ID（写事件载荷、写审计目标），依赖数据库返回会把一个事务拆成多次往返。

也不要自增主键：值可枚举（订单号能猜），跨表批量写要等 nextval，分区表下还要全局序列协调。

### 金额存精确十进制（`BigDecimal`），禁浮点；出参序列化成字符串

DB 用精确十进制（PostgreSQL 的 `numeric`），Java 用 `BigDecimal`，**禁 `float`/`double`**。
出参走 JSON 时把金额序列化成**字符串**，前端只做展示、**不参与任何计算**。

**理由不是「`BigDecimal` 会算错」**——精确十进制算钱数学上没问题，禁浮点是因为
`float`/`double` 的 IEEE754 在跨层时静默丢精度。真正的坑有三处，都是「不报错的错」：

- `BigDecimal.doubleValue()` 是**编译器不拦的静默降级通道**——转成 `double` 就掉进 IEEE754
- `equals` 比 scale 而 `compareTo` 不比——`new BigDecimal("1.10").equals(new BigDecimal("1.1"))`
  是 `false`，坑 `HashSet` 和断言；金额比较一律 `compareTo`
- 序列化成 JSON number 之后，JS 的 IEEE754 又把精度绕回来——前端求和会显示 `3600.0000000000005`

所以出参金额**序列化成字符串**（`toPlainString()`，去科学计数法、保留原 scale），前端拿字符串
只展示不 parse。纪律：金额比较用 `compareTo`、运算显式 `setScale`、出参走字符串化注解。

### 外键列一律建索引

PostgreSQL 不自动建外键索引；漏了之后删父行、级联锁检查、按外键过滤都会退化成全表扫。

### 迁移：手写版本化 SQL，ORM 不碰 schema

schema 用版本化迁移脚本管（`up`/`down` 成对），ORM 不参与建表/改表（禁 `ddl-auto` 这类启动时静默改表）。破坏性变更走「扩展 → 双写 → 切换 → 清理」分阶段，保证滚动发布窗口里新旧两版都能跑；生产不直接 `DROP COLUMN`。

## 事务与并发

### 写操作必须事务

新增 / 修改 / 删除这类写操作一律在事务内执行；没有事务环境就执行写，直接抛异常或拒绝，不许裸写。

### 事务加在事务层（编排层），下层不开事务

`@Transactional` 加在事务层（编排层，项目里通常叫 Service 层）的方法上；下层方法不自己开事务，被事务层调用时随外层事务走，被旁路（定时任务等）调用时由旁路入口自己包事务。

### 嵌套事务按场景区分，不做绝对禁止

默认不用 `REQUIRES_NEW` / `NESTED`——它让「一半提交一半回滚」成为可能，金额、编号、配额这类业务数据一旦半提交就是静默损坏。确有独立提交需求的场景才用，且要清楚它不受外层回滚保护。

判据：**这个操作失败时，应不应该跟着业务一起回滚？** 应该 → 同事务；不应该（独立留痕）→ 才考虑独立事务。

### 外部副作用不进业务事务

发邮件、调支付这类外部副作用不在事务里同步做——它没有事务，回滚带不动它，耗时还反过来拖死行锁。业务变更与「要发副作用」这件事（事件 / outbox 表）同一事务落下，事务提交后由独立投递器异步执行。

### 写操作幂等

凡是可能被客户端重试的写，要求带幂等键，服务端存「键 → 首次响应」：同键 + 同请求体返回首次结果不重做，同键 + 不同请求体返回 409。网络重试是常态，没有幂等就等于接受重复执行。

### 并发修改用乐观锁，不用「先读后写」

会被多人同时编辑的资源带 `version` 列：响应带 `ETag`，保存带 `If-Match`，UPDATE 写成 `set version = version+1 where id=? and version=?`，影响 0 行返回 409「已被他人修改」。否则后保存的静默覆盖先保存的。

### 唯一性与时间区间不重叠，落 DB，不靠应用层「先查再插」

业务编号唯一、身份有效期不重叠这类约束，用数据库唯一约束 / 排他约束（`EXCLUDE USING gist`）表达，DB 拒绝就捕获转 409。应用层「先查有没有再插」在并发下永远有缝隙。

## 代码习惯

### 方法参数超过三个就封装成对象

**目的是可读性**——防止出现一个请求塞 30+ 个参数那种东西。不是为了类型安全。

### 接口入参能放一起就放一起，不拆到多个位置去读

**不是拒绝 RESTful——是减少读代码时要看的地方。** 一个操作的入参散在路径、查询串、body 三处，
读的人要在三处拼出完整画面，还多出「路径的 id 与 body 的 id 对不上算谁的」这种本不该存在的问题。

- **写接口（有 body）**：参数全进 body，资源 id 也进，不留「路径 id + body 其余」的双来源
- **读接口（GET 没有 body）**：路径寻址或查询串本来就是一处，不受影响，不必为统一把读也改成 POST
- 写动作统一 POST——DELETE 携带 body 兼容性差，语义收益撑不起兼容成本
- id 进了 body 就是普通必填字段：照常 `@NotNull` + 「漏传 → 400」测试——它的缺失从路由层的
  404 变成了绑定层的校验责任，**防线要跟着搬，不能两头都没有**

与下一条「形状一致就直接传 Req」合起来，读代码是一条直线：
body → Req（一处装齐全部入参）→ service（同一个对象），中间零拼装。

### Req 能不能传进 service：看形状分不分叉，不看「它是不是 HTTP 类型」

**校验与类型无关，永远两层**：注解在绑定层管格式（也只能管空值/长短/范围这类简单项）；
跨字段条件（「A 为某值时 B 不得大于 C」）、状态依赖这类业务校验**永远在 service**，
不因为传的是 Req 还是重新封装的对象而增减一条。

**类型转换不是控制机制**——它不产生校验、不阻止任何调用方（谁调 service 就构造什么类型，
成本一样）。不要赋予它安全含义，也不要拿「service 将来有非 HTTP 调用方」当建第二个类型的理由。

**只在形状真的分叉时才建独立的 Cmd/参数对象**：

- **服务端决定的字段**——HTTP 端必须不可传（如禁用原因，客户端不许自选）、而定时任务端必须能传。
  Req 与 Cmd 各自的形状都对且不相等，这才是分叉
- **多入口不同形状汇聚到同一个 service 方法**
- 路径参数 + body 直接 `(id, req)` 两个参数传，不算分叉，不必为合并发明一个 Cmd

形状一致就直接传 Req。同形的 Req→Cmd 逐字段手搬是两头的坏处全占：
付了双类型的维护费，还把字段错位的 bug 藏进缝里（同类型位置参数对调，编译器无感）。

### 注释写「这段代码是什么、怎么走」，不写「它怎么变成这样的」

好注释的形状：**先一句总结这段代码在干什么；逻辑多步的，跟着列具体步骤；最后补代码自身
表达不了的约束**（为什么必须这样写、动了会坏什么）。简单代码只要第一句，别把 getter 也写成清单。

历史分两档，处理方式相反：

- **同一个需求开发过程中的迭代——第几轮修复、哪次评审、改过几版——一律不进注释。**
  交付时只有终态，过程归 commit message 和评审报告。需求没交付完，代码里就不存在「老逻辑」。
- **交付之后真的改了既有逻辑，可以留一条变更注释**：`时间 + 更新人 + 老逻辑 + 新逻辑`，
  一两行说清。它是变更记录不是叙事——同一处后来又改，就更新那一条，不要叠罗汉。

判据：**除变更记录行外，把注释里的日期、任务号、轮次号删掉，句子还成立吗？**
不成立，说明写的是过程不是逻辑。

约束类注释保留，但用无时态的方式写：

- ❌「评审 F2 修复轮次 1：此前用完整编号导致测不出前缀匹配退化，现改为部分前缀」
- ✅「查询值必须是部分前缀而不是完整编号——完整编号下等值匹配与前缀匹配结果相同，测不出退化」

### `//TODO` 要写清缺什么

反例：`//TODO 待实现`。
正例：`//TODO(<依赖>) <缺哪张表 / 哪个方法 / 阻塞于哪条需求编号>`。**让下一个人不必重新调研。**

### 不要留做不到的承诺

注释和文档里写下的保证（「这条测试会在 X 变化时变红」），**要么真的做得到，要么不要写**。
做不到就如实写明覆盖边界在哪。一句做不到的承诺比没有承诺更糟——它会让人停止再找防线。

### HTTP 状态码语义自洽

业务规则冲突用 409，请求格式错用 400，不用 422。列表接口强制分页 + 稳定次级排序键，否则翻页会漏行或重复。

## 测试纪律

### 严格 TDD，且「确认失败原因」这步不能省

写失败的测试 → 跑它 → **确认失败原因是你预期的那个** → 再写实现。
很多失败长得一样却成因不同（路由不存在和资源查不到都可能是 404），不确认就等于没测。

### 每条断言都要能回答：它在什么情况下会假

想不出来就是没测到东西。常见的假绿：

- 断言恒真
- **测试名承诺的范围宽于断言能验证的范围**（名字叫「前缀匹配」却拿完整值去查）
- 只断言 HTTP 状态码，不断言业务码
- 该排他的地方用了 `contains`（断言「只改了 A」用 `contains("A")`，改了三个字段也照样通过）

### 要证明一条测试有牙齿，就临时把实现改坏

看它是否真的红、**且红在你预期的那一行**，把红色输出留进报告，再改回。
对架构规则、契约测试这类「静默通过就等于没有」的检查，这一步是强制的。

### 报告里的数字必须来自真实运行

测试数、通过数一律贴构建工具汇总行原文，**不许自己算**。算出来的数字会被后来者当事实引用。

### 集成测试必须真库

涉及 SQL、约束、索引、锁、RLS 的集成测试连真实数据库（Testcontainers 这类），不用 SQLite / H2 等替身——方言与特性在替身上测不到，测了也是假绿。

## 安全与正确性

### 一次公开动作 = 恰好一条真实审计

不多不少，且**内容属实**——不能记一条「更新了 A、B、C」而实际只改了 A。
用精确条数断言钉住。**查询接口一条都不许写。**

### 越权取数返回 404，不是 403

**403 等于承认这个 id 存在。** 按 id 取一条不属于你的数据，回 404——让「无权访问」与
「根本不存在」在响应上无法区分，否则接口本身成了一个存在性探测器。

### 表所有权唯一

每张表只有**一组** entity/Mapper/Dao 和**一个** owner service。要别人的数据就调 owner 的方法，
**禁止为同一张表写第二组 Mapper**。第二组一出现，那张表的约束、软删过滤、租户过滤就有了两份实现，
迟早对不上，而且不会有任何东西报错。

### 用户可见文案禁硬编码

一律走统一的错误码 + i18n key，各语言文件同步齐全，**用测试卡住「每个码各语言齐全」**，
否则漏一条只有用户会发现。

### 5xx 不回显内部细节

堆栈、SQL、三方报错只进日志，对外只给通用文案 + `traceId`。

### 时区全链路固定一个，不做双时区换算

时间戳统一带偏移量的类型（`OffsetDateTime` 这类）。**双时区换算是错误的温床**——
每多一处换算就多一个可能漏换或换反的地方，而这类错误只在跨越边界时显现。

### 禁 Jackson 多态类型解析

禁 `activateDefaultTyping` 与 `@JsonTypeInfo`——这是 Jackson 反序列化 RCE 的唯一前提。
确需多态用白名单式 `@JsonSubTypes` + `Id.NAME`，并附安全评审。用测试拦住。

### 对象转换走代码生成，禁反射拷贝

反射拷贝（`BeanUtils.copyProperties` 这类）在字段改名后**静默不拷**，编译器不报错、测试也常常照过。
用 MapStruct 这类编译期生成的方案，字段对不上时**编译就失败**。

### 隔离机制若是 fail-closed，测试必须有正向对照

这类机制常常「不满足条件就静默返回空集」，表现和「资源根本不存在」一模一样。
所以越权测试要**先用有权限的上下文打同一路径断言成功，再切换到无权限断言空**——
只断言失败码分不清「防线生效」与「路由写错了」。

### 敏感字段出参用整串扫描，不要列白名单

扫整个响应 JSON 找禁止出现的字段名（先统一大小写），这样响应体新增字段会被自动覆盖；
白名单要靠人记得回来更新，迟早漏。

**但脱敏要看用途**：如果详情接口同时是编辑表单的数据源，而更新接口又要求那些字段必填，
**详情就不能脱敏**——否则掩码字符串会被回显、然后当真值写回库。这是静默的数据损坏。

### 审计 append-only，数据库层收回写权限

审计日志不提供任何 UPDATE / DELETE 接口，数据库层直接收回业务账号对这些表的 UPDATE / DELETE 权限。「一次动作一条审计」是应用层纪律，挡不住写代码绕过；DB 权限是物理兜底。

### 密钥不入库、不入 git、不入 CI

密钥（数据库密码、JWT 密钥、支付密钥）只进部署机或 Secret Manager，禁止硬编码进代码、commit 进 git、写进 CI 变量明文——一旦进 git 历史，改密码也救不回来。必填配置启动时断言，缺了就失败，不用默认值静默启动。

## 给建议时的纪律

- **先查文档再答**，不要凭通用经验现编。表怎么建、字段什么含义，项目文档里通常已经写了。
- **区分「已定」和「待定」**。项目里往往有专门的待决策项清单——那里面的东西**不要当成已定口径**
  去设计，用它反而会把一个未决问题伪装成既成事实。
- **下「文档没写 / 需求缺失」的结论前，必须回原始来源确认。** 导出、二手整理、别人的摘要都可能有损
  （见过一份导出丢掉了 137 条判定里的 114 条）。原型/原始文档才是源。
- 引用任何类名、文件名、配置项、编号之前**先 grep 确认它存在**。引用一个从未落地的东西，
  会让后面的人当既有事实继续传播。

## 工作方式

1. **开工前核对现状**：分支、工作区是否干净、HEAD 是否与简报一致，对不上就报
2. **每完成一个可提交单元就提交**，不要攒到最后；提交用明确文件路径，**不要 `git add -A`**
3. 做完跑完整测试，确认既有测试没被打破

## 发现问题就报，不要替我圆场

简报和我给的建议**都可能是错的**。我要的是：

- 觉得矛盾**先问再动手**，不要一边猜一边写
- 用实验纠正我的错误建议（「我试了，你说的做法在这里不成立，证据是……」）
- **自曝自己写的测试其实测不到目标**——这比交一份看起来漂亮的报告有价值得多

## 成功指标

- 每条测试都能说清「它在什么情况下会红」
- 缺口都有 `//TODO(<依赖>)` 写清缺什么，下一个人不必重新调研
- 报告里没有一个未经真实运行的数字
