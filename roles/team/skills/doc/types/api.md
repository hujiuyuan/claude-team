# 功能与接口设计

## 前置卡口

**需求分析必须是成品**——标题下没有「⚠️ 未完成」那行，全文没有未决项。带着没定的口径设计接口，接口形状是按假设定的。

---

## 一、先决定出几份文件

**判据：读的人能不能一屏看完接口清单。** 看不完，功能长什么样就被接口细节淹了。
经验阈值 **5 个**，但以「一屏」为准，不以数字为准。

### 不拆（接口 ≤ 5）

一份文件：

```
1     这是什么功能
2     功能生命周期
3     接口清单
4..N  每个接口的明细（一个接口一节）
```

### 拆（接口 > 5）

两份文件，**命名固定**：`<功能名>-功能设计.md` · `<功能名>-接口明细.md`

**`<功能名>-功能设计.md`**

```
1  这是什么功能
2  功能生命周期
3  接口清单   | URL | 方法 | 干什么 | 明细 |
```

接口清单比不拆时**多一列「明细」**，填指向明细文件的可点锚点：

```markdown
| `/api/coupon/grant` | POST | 用户领券 | [明细](优惠券-接口明细.md#用户领券) |
```

🔴 **功能设计里不许出现请求参数表、响应结果表、伪码、接口级的图。** 出现了就是没拆干净——那等于两份文件都要读，拆了个寂寞。生命周期图是例外，它属于功能不属于接口。

**`<功能名>-接口明细.md`**

```
头部一行指针：← 功能背景与生命周期见 <功能名>-功能设计.md
每个接口一节：URL 与方法 / 请求参数表 / 响应结果表 / 处理逻辑 / 图
```

🔴 **明细里不许重复功能背景。** 只留头部那一行指针。重复一遍的后果是两份分叉，而且没人知道哪份是对的。

### 再拆一层：一个接口一份文件

接口明细单份还是读不动时，**每个接口拆一份**。判据两条，命中任一条就拆：

- 单份明细里的接口**超过 8 个**
- **单个接口自己就超过一屏**（伪码 + 两张参数表 + 时序图，复杂接口很容易到）

拆完变成三层：

```
功能设计（一份）          是什么 + 生命周期 + 接口清单
  └── 接口文件（每接口一份）  URL / 请求参数表 / 响应结果表 / 伪码 / 图
```

**中间那层「接口明细」整份消失**，不要留一个只有目录的空壳——接口清单本身就是目录。

### 命名：逐层加一段，用 `-` 隔开

**每加一层就在文件名后面追一段，前缀原样保留。** 这样只看文件名就知道它属于哪个功能，不用先看路径。

```
优惠券-功能设计.md
优惠券-01-用户领券.md
优惠券-02-我的优惠券.md
优惠券-03-运营建券.md
```

🔴 **项目已经有编号体系的，沿用它，不另起一套。** 有编号时前缀就是那套编号，规则不变——逐层追加、前缀不动。项目的编号规则文档比本节优先。

三条硬约束：

1. **号一旦分配就不复用。** 文档删了，号也不给下一份——台账和别处的引用会指错地方
2. **作废的改名加 `-作废` 后缀，文件保留。** 直接删掉，指向它的条目就悬空了
3. **未决项单独成一份文件，不混进正文。** 没有未决就不建这个文件

### 三层之间的对账

**接口清单的行数 == 所有明细/接口文件里的接口数。** 对不上就是漏了——要么清单里有项没人写，要么有个接口没进清单（那就是没人调的孤儿）。

## 二、功能设计写什么

```
1  这是什么功能    一段话：给谁用、解决什么问题、本期做到哪、本期不做什么
2  功能生命周期    从开始到结束经过哪几个状态、谁推动状态变化
3  接口清单        | URL | 方法 | 干什么 |
```

### 1 · 这是什么功能

**第一句就要让人知道在说什么。** 写「用户领取满减券，领了能在我的券列表看到，到期自动失效」，不写「本文档描述优惠券模块的设计方案」。

### 2 · 功能生命周期

**一句话说得清就写一句话**，说不清就画 `mermaid flowchart`。
判据：状态超过三个、或有分支、或有定时/异步推动的环节 → 画图。

**生命周期图直接决定接口数量。** 图上那些**不由用户点击推动的边**（「定时任务扫到期」这种），对应的是定时任务或消息消费者，不是接口——但它们照样要进接口清单，漏了生命周期就断了。

### 3 · 接口清单

| URL | 方法 | 干什么 |
|---|---|---|

定时任务和消息消费者也列进来，URL 那列写任务名 / topic 名。

## 三、接口明细写什么

每个接口五样，固定顺序：

```
1  URL 与方法
2  请求参数表      一张
3  响应结果表      一张
4  处理逻辑        分步伪码，写接口必有
5  图              按下面的判据选，简单的不画
```

### 1 · URL 设计：尽量避免 RESTful

**路径里带动词，一个动作一个路径，不靠 HTTP 方法区分语义。**

| 别这么写 | 这么写 |
|---|---|
| `PUT /coupons/{id}` | `POST /coupon/template/update` |
| `PATCH /coupons/{id}` | `POST /coupon/template/publish` |
| `DELETE /coupons/{id}` | `POST /coupon/template/end` |

**为什么**：「审核通过」该用 `PUT` 还是 `PATCH` 永远吵不出结果，吵赢了也没收益。动词化路径有两个实际好处——**权限点按路径配比按「方法+路径」配简单**，翻日志一眼看出是哪个动作。

读接口 `GET`，写接口一律 `POST`，两种够用。

### 2、3 · 请求参数与响应结果：两张表，不合并

**请求参数**

| 参数 | 类型 | 含义 | 必填 | 取值来源 |
|---|---|---|---|---|

**响应结果**

| 字段 | 类型 | 含义 | 可空 | 说明 |
|---|---|---|---|---|

硬规则：

1. **第一列写代码里真实的键名**，中文只进「含义」列
2. **类型单一确定**，不写「A 或 B」
3. **枚举字段给机器可读的取值**——只写「待审核 / 已通过」，前端不知道传什么、收到什么
4. **从登录态取的东西不许出现在请求参数表里**（`userId`、`tenantId`）。列进去等于开越权口子
5. **金额、时间的单位和格式写在「含义」列**：元还是分、字符串还是数字、带不带时区

### 4 · 处理逻辑：分步伪码

**每个写接口都要有。** 粒度是**分步伪码，不是方法体实现**。

```
① 幂等查重    按 (租户, 模板, 用户) 唯一键，命中已成功的直接返回
② 状态守卫    草稿 / 停发 / 结束 → 40102；发放中 → 继续
③ 有效期守卫  未开始 → 40103；已过期 → 40104；区间内 → 继续
④ 原子自增    UPDATE ... WHERE 总量=0 OR 已领数<总量，看受影响行数
              0 行 → 40105 已领完
⑤ 落记录      插入，唯一键冲突则回滚 ④，返回 200「已领取」
──────────── 以上 ①~⑤ 同一事务 ────────────
⑥ 触发下游    走事务提交后的钩子，不与 ①~⑤ 共存亡
```

四条硬规则：

- **带编号，每步一句话**
- **标出事务边界**——哪几步同一个事务、哪几步在提交之后。用分隔线或直接注明
- **凡是列举，每一项都给处置**。「校验四项」要写四项各自不通过怎么办；「状态守卫」要写所有进来的状态各走哪条路，不许只写放行的那两个；有成功/失败两个分支就两个都写；有阈值要**说清 `0` 是什么意思**
- **伪码之后补边界**：哪一步失败要怎么办、**哪些失败不许回滚**（钱已经收了）、哪条路径走另一个分支

### 5 · 图：三选一

| 情况 | 画什么 |
|---|---|
| 只涉及一个对象、几个分支、状态流转 | `mermaid flowchart` |
| **两个以上参与者**、有明确先后（调第三方、异步、回调、重试） | `mermaid sequenceDiagram` |
| 线性三五步、没有分支 | **不画**，伪码够了 |

**时序图必须带失败分支。** 只画正常路径的时序图是假的——真正会出事的全在失败分支里：

```
Note over 服务端: —— 失败分支 ——
```

至少画出：对端超时 · 对端返回失败 · 重复请求进来 · **中途某步失败但前面的副作用已经发生**。最后一种最关键——钱已经收了但发货失败，不能因为发货失败把订单退回未支付。

**service 层的复杂逻辑用图，不列成接口清单**——它没法通过 HTTP 直接测，图是解释「逻辑怎么做」的手段。

## 四、非 HTTP 入口补四问

定时任务、消息消费者、第三方回调**不能只写「干什么」**：

| # | 问 | 为什么是这四个 |
|---|---|---|
| 1 | **触发与去重** | 多实例部署会不会同时跑？靠什么去重？ |
| 2 | **上下文从哪来** | **没有请求，租户值和操作人必须自己设。** 启用了行级安全的表，不设租户值查不到任何一行**而且不报错**——表现是「跑成功了但一条没处理」 |
| 3 | **幂等** | 重复进来会怎样？上一轮没跑完这轮又到点了怎么办？说了「要幂等」必须说**用什么机制** |
| 4 | **失败怎么办** | 重试几次、耗尽落哪、单条失败是跳过还是整批中止 |

**回调额外一条**：对方要什么格式的应答——**答错会被一直重推**。

## 五、Review 检查清单

**review 时过的，不是要写进文档的内容。**

- [ ] **拆了的**：接口清单行数 == 所有明细 / 接口文件里的接口数吗
- [ ] **拆了的**：功能设计里有没有混进参数表 / 伪码 / 接口级的图——有就是没拆干净
- [ ] **拆了的**：下层文件有没有重复功能背景——只该留头部一行指针
- [ ] **拆了的**：清单里「明细」那一列的锚点点得开吗
- [ ] **拆到接口级的**：中间那层「接口明细」整份删掉了吗——不要留只有目录的空壳
- [ ] **拆到接口级的**：文件名前缀一路带着走吗——单看文件名能不能看出属于哪个功能
- [ ] 作废的文件加了 `-作废` 后缀并保留吗，号有没有被复用
- [ ] **密度**：有没有把一格能装下的事实另起一段再补推导——挑三段正文，逐段问「这段里有没有哪句该在某个表格的格子里」，有就搬回去
- [ ] **密度**：禁用语 `grep` 零命中（命令见 `SKILL.md`），表格单元格没有超 60 字的
- [ ] 生命周期图上每一条边，都能对上接口清单里的一项吗——对不上就是漏了接口或漏了定时任务
- [ ] 接口清单里每一项，都在生命周期里有位置吗——没有的就是没人调的孤儿
- [ ] **每个写接口都有分步伪码吗**，伪码里标了事务边界吗
- [ ] **凡是列举，每一项都给了处置吗**——校验四项写了四项？状态守卫写全了所有进来的状态？成功和失败两个分支都写了？阈值说清 `0` 是什么意思了？
- [ ] 两个维度交叉时，说清哪些组合根本不成立了吗
- [ ] **有第三方 / 异步 / 回调的，画时序图了吗，带失败分支了吗**
- [ ] 出参形状跟已有的下游契约**逐字对齐**了吗（含返回体的包装形状）——对不上的典型后果是前端每次成功请求都报「失效」
- [ ] 时间词有没有写成「当天」「不晚于今天」——**要说清是精确时点还是自然日、按哪个时区、用哪个常量**
- [ ] 改已有接口：老客户端不升级能不能工作？**枚举加值会不会让下游的穷尽断言爆炸**？
- [ ] 同一个业务动作，多个入口是不是共用一处实现——判据是「删掉任意一个入口，实现代码一行都不用改」
