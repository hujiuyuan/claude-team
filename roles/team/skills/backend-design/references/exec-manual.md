# 执行手册

**真理源边界**：执行手册是「按什么顺序做」的唯一真理源。任务顺序、改哪些文件、完成判据只能写在这里。
**不许复述**接口签名、字段表、建表语句——只写指针（"入参见设计文档 4.2 的 `PayInitCmd` 字段表"）。
**判据：手册里出现代码块（命令行除外）即越界。**

头部固定记三个指纹：PRD 的 sha256 · 代码仓库 commit · 上一轮产物路径。

---

## 一、切任务

任务不会自己冒出来，切任务是一道独立工序。

### 三条判据

**1. 主线任务沿链路切，支线任务按落点切。**
主线任务每个推进"入口 → 价值兑现"这条链路一段；支线任务按它挂在链路的哪个落点上切。

**2. 一个任务必须有独立的完成判据。**
- 判据跟上一个任务重复 → 切太小了，合并
- 一条命令验不完 → 切太大了，拆开

这是最实用的一条：切不出独立命令的切法，就是错的切法。

**3. 一任务 = 一 PR = 一会话。**
上界是**一个会话的上下文装得下**：要改的文件 + 要抄的参照实现 + 相关设计小节，加起来读得完。

### 排序：主线优先

先把主线任务排成一条**能端到端跑通的最短路径**，支线挂在后面。

每一批标注：**这批做完之后，主流程能不能端到端跑通一次。**

好处是随时能停——已完成的部分是能用的，而不是做到 80% 却什么都跑不起来。批次依赖用文本树画：

```
第 1 批（互不依赖，可并行）
  ├─ ...
  └─ ...
第 2 批
  └─ ...          ← 这批做完，主流程首次端到端跑通
```

## 二、预检冲突扫描

**同批可并行的任务两两比对**，扫三样：

| 扫什么 | 冲突长什么样 |
|---|---|
| 共享文件 | 两个任务都要改同一个文件（登记表、枚举类、配置类最容易撞） |
| 共享接口 | 一个任务定义、另一个任务调用，形状要先对齐 |
| 共享枚举 / 常量 | 两个任务各加各的值，合并时撞号 |

**冲突要预先裁定，不留给执行时现场协调**：谁改、别人只读、按什么顺序合。裁定结果写进手册首屏，派活前生效。

典型高危：迁移脚本编号、错误码段位、权限点登记表、统一的匿名端点白名单——这几样天然是全局单文件，几乎每批都会撞。

## 三、每任务八段

```
### 任务 X · <做完是什么样，一句话>

1 入口与作用
2 前置
3 改哪些文件
4 抄谁
5 不许碰
6 怎么做
7 本任务的坑与关注点
8 完成判据
```

### 1 入口与作用

**本任务新增的每个东西，从哪个入口能到达、在那条链路的第几阶段起什么作用。**
写不出这一段，说明任务没想清楚，不许往下写。

例："新增的 `XxxGuard.check()` 挂在 HTTP 入口 `POST /a/b` 的第 7 阶段（业务执行）里，由 `AaaServiceImpl.approve()` 调用；同时被定时任务 `BbbJob` 的第 7 阶段调用——**所以租户必须显式传参，不许从线程本地变量摸**。"

**`S` 档的入口四格也写在这一段**——上下文建立 / 幂等与并发控制 / 出口 / 失败与留痕四格必答。`S` 档没有设计文档 4.0 节，这四格在这里答，判据同 `entry-points.md` 的「带 ★ 四格永远必答」。

### 2 前置

依赖哪些任务已完成、开工前要确认的事。

### 3 改哪些文件

**精确路径，从仓库根算起。新建与修改分开列。**

```
新建
  src/main/java/.../XxxService.java
修改
  src/main/java/.../PermRegistry.java     加两颗按钮键
```

模糊路径（"相关的 service"）不算数。

### 4 抄谁

**仓库里已有的同形状实现 + 抄它哪一段 + 哪一段不能抄。**

这一段对刚接手的人最管用，比任何抽象描述都有效。写法：
"照 `ClubApplicationServiceImpl` 的 `approve` / `returnBack` / `reject` 三个动作抄结构；**但它的租户解析那段不要抄**，那条路径有请求上下文，本任务没有。"

没有可抄的就写"仓库里无同形状实现"，不留空。

### 5 不许碰

明确禁区。常见：别的模块 owner 的表、已经跑过的迁移文件、别人负责的假件（不许自己编一个顶上）、正在被另一个并行任务改的文件。

### 6 怎么做

分步，每步一句话。涉及的数据结构**指回设计文档具体小节**，不复述。

### 7 本任务的坑与关注点

**这一段装两样形状不同的东西**：坑（三段式）和 S 档的通用关注点。别混写。

**坑**——从全局坑清单里挑出跟这个任务相关的，按三段式写（症状 / 原因 / 正确写法）。全局坑清单的正文在**设计文档第 7 节「坑清单与技巧表」**（`S` 档在本手册的全局章节），这里只挑不复述。形状见 `writing-shapes.md`。

**不是把全局二十条都抄一遍**——挑相关的三五条。全抄等于没挑。

**`S` 档通用关注点的唯一落点在这里**：十类里跟本次改动直接相关的几类（金额精度 / 时区 / 缓存 / …），按 `cross-cutting.md` 的「要写清什么 / 判据」写，不涉及的不写、不逐类凑「不涉及」。这是「坑」之外的并列项，形状不同，别混成三段式。

### 8 完成判据

**一条能跑的命令 + 期望输出。**

```bash
mvn -q test -Dtest=XxxServiceTest
```
期望：3 个用例全绿，其中 `shouldRejectDuplicateCallback` 断言 `txn` 表只多一行。

**禁止**："实现完成"、"功能正常"、"接口可用"、"测试通过"（哪个测试？跑什么命令？）。

写不出命令的任务，说明没拆到底——回第一节重切。

## 四、完整范例：一个填满的任务八段

规则看十遍不如范例看一遍。下面是一个真实形状的任务，八段全填，照这个密度写。

---

### 任务 A-10 · 入账函数落地：线上回调 / 后台登记 / 线下审核三条路都调它，走完订单转已支付且流水收据齐全

**1 入口与作用**

本任务新增的 `PaymentPostingTx.post()` **不是入口**，是三个入口共用的落点：

| 入口 | 类型 | 落在第几阶段 |
|---|---|---|
| `POST /portal/{tenantCode}/pay/callback/{provider}` | 回调 | 第 7 阶段 业务执行 |
| `POST /tenant/orders/{orderId}/pay`（后台登记线下收款） | HTTP | 第 7 阶段 业务执行 |
| `POST /tenant/offline-proofs/{id}/review`（线下凭证审核通过） | HTTP | 第 7 阶段 业务执行 |

三入口取交集，推出三条**硬约束**：

- 回调入口没有登录态、没有可信的 Host → **租户必须从路径段显式传入，不许从线程本地变量摸**
- 回调会被网关重复推送 → **必须可重入**：同一 `(provider, merchant_id, provider_event_id)` 第二次进来直接返回首次结果
- 三条路共用一处实现 → 判据是「把任一入口整个删掉，本函数一行不用改」

回调入口的四格必答见设计文档 4.0.2 的回调那一栏。

**2 前置**

- A-04（支付插口 + 假网关）已合并——本任务要写 `payment_attempt`，那张表的 DAO 归 A-04
- V86 迁移（交易设置表）已跑——第 ⑦ 步开收据要读 `order_cfg.autoZero`
- 开工前确认：`origin/dev` 上 `PaymentAttemptDao` 已存在，三列联合查询可用

**3 改哪些文件**

```
新建
  src/main/java/com/example/gym/service/PaymentPostingTx.java           接口
  src/main/java/com/example/gym/service/impl/PaymentPostingTxImpl.java  唯一实现
  src/main/java/com/example/gym/model/cmd/PostingCmd.java               入参
  src/main/java/com/example/gym/model/resp/PostingResult.java           出参
  src/test/java/com/example/gym/service/PaymentPostingTxTest.java
修改
  src/main/java/com/example/gym/common/exception/OrderResultCode.java   加「金额不符」「状态不允许」两个码
  src/main/resources/i18n/messages*.properties                            四份都加，缺一份构建就红
```

**4 抄谁**

照 `OutboxDeliveryTx` / `OutboxDeliveryTxImpl` 抄「**单独立一个承载事务边界的接口**」这个结构——它就是为了绕开「`service.impl` 的 public 方法禁互调」这条架构约束而存在的成例，形状一模一样。

**不要抄它的重试与死信那部分**：发件箱失败可以重投，入账不行——钱已经收了，重投会重复入账。

**5 不许碰**

- `txn` / `receipt` 两张表只有 INSERT 权限，别写 UPDATE 语句——冲正靠新增反向行
- 已跑过的 V77~V81 迁移文件一律不动，要订正列注释走新迁移的 `COMMENT ON COLUMN`
- 配额校验 `MemberQuotaGuard` 是别人负责的接缝，恒放行是临时状态——**别当业务规则用，也别自己去实现它**

**6 怎么做**

一个事务里按序八步：

```
① 幂等查重 → ② 落 payment_attempt → ③ 校验商户/金额/币种/订单关联
→ ④ 状态守卫 → ⑤ 订单转已支付 → ⑥ 写 txn → ⑦ 开 receipt → ⑧ 触发生效
```

每步的字段与判据见**设计文档 4.3「入账函数」**，这里不复述。两条边界：①~⑦ 同一事务；**⑧ 走事务提交后的钩子**，不与前七步共存亡——生效失败不许把已收的钱回滚。

**7 本任务的坑与关注点**

> **症状**：金额不符的回调进来，订单照样转成已支付、身份也生效了，全程不报任何错。
> **原因**：第 ③ 步只判了金额非空没判数值；或者判了但用 `double` 相减判零。
> **正确写法**：`BigDecimal.compareTo` 判等（**不用 `equals`**——标度不同会误判不等），不符则置 `result=amount_mismatch` + 建人工任务 + 抛业务码，**绝不往下走**。

> **症状**：网关重复推送两次，`txn` 多了一行、收据开了两张，对账那天才发现。
> **原因**：幂等键拼成了单列字符串，两次推送拼串顺序不同就没命中。
> **正确写法**：幂等键是 `(provider, merchant_id, provider_event_id)` **三列联合查询**，不拼串。

**关注点 · 金额精度**：金额一律 `BigDecimal`，禁 `double`/`float`；手续费按 `pay_channel.rate` 现算不写死；`net = amount - fee - platform_fee` 中间步骤不各自舍入，只在落库前舍一次。

**8 完成判据**

```bash
mvn -q test -Dtest=PaymentPostingTxTest
```

期望 5 个用例全绿：

| 用例 | 断言 |
|---|---|
| `shouldPostOnce` | 正常回调 → `txn` 多一行、`receipt` 一张、订单转 `paid` |
| `shouldBeIdempotent` | 同一三元组调两次 → `txn` 仍只多一行、`receipt` 仍只一张 |
| `shouldRejectAmountMismatch` | 金额少 1.00 → 订单**不转** `paid`、`manual_task` 多一条 |
| `shouldNotEffectOnLatePaid` | 订单已 `expired` 时回调 → `txn` 多一行、`receipt` **零张**、生效动作**零次调用** |
| `shouldRejectUpdateOnTxn` | 用受限角色对 `txn` 执行 UPDATE → 报权限错 |

## 五、全局章节（不在每任务里重复）

手册末尾放这几节：

**提交约定**——分支从哪切、commit 信息格式、PR 描述要带什么、合并前要过什么。

**上线与回滚**——部署顺序（先库后代码还是反过来、新旧代码能否并存）、回滚方案（代码 / DDL / 数据各怎么回）、灰度与 feature flag、数据迁移脚本的排期。见 `cross-cutting.md` 第 7 类。

**红线自检表**——合并前逐条勾的清单。挑真正会出事的写，十几条封顶；写成三十条没人会看。

**坑清单与技巧表（仅 `S` 档）**——`M`/`L` 档这两张表在设计文档第 7 节，本手册不重复。`S` 档不出设计文档，两张表落在这里：坑三段式、技巧四列，形状与采集工序见 `writing-shapes.md`。

**销号区**——每个任务做完在这里标 ✅ 并附证据（PR 链接 / 命令输出）。

## 六、盲测抽检

写完手册要验，标准是**能不能脱离上下文照着干**。

**做法**：随机抽任务，**只读该任务那一节 + 它明确指到的设计小节**，其余内容当作看不见，逐条核对：
- 能不能写出编译通过的骨架？
- 有没有需要回头问的问题？

有任何一项答"否"，那一节不合格，打回重写。

**抽样量**：`L` 档抽 3 个，`M` 档抽 1 个，`S` 档免。
要真开一个干净子会话来跑，先问用户。

**逃生口**：同一节连续两次不过 → 判定为**任务切错了**，回第一节重切，**不许继续磨手册措辞**。反复改措辞而不重切，是这套流程最容易陷进去的死循环。
