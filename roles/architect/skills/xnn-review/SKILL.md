# X-NN 需求分析规划

参数：$ARGUMENTS

由主会话主持。参与者：

- `architect:architect`：需求基线、YY 拆分。
- `team:debater`：视角审计员或代言人。
- `team:judge`：裁判。
- 主会话：写文件。写作量大时可以交给 `writer:writer`。

先读本目录下的清单和模板：

- [coverage-checklist.md](coverage-checklist.md)：PRD 覆盖
- [lifecycle-matrix.md](lifecycle-matrix.md)：生命周期闭环
- [executability-checklist.md](executability-checklist.md)：可执行性
- [xnn-skeleton.md](xnn-skeleton.md)、[yy-template.md](yy-template.md)：没有样板时用的通用骨架

## 规则

- **遇到问题按 house-rules 分级**：能查到的查（L0）；需要判断的一律走 `team:deliberate`（L1）；只有 L2 才问用户，而且在阶段末一次问完。
- **运行目录**：`~/.claude-team/runs/<YYYYMMDD>-<X-NN>/`，问题池、各轮原文、裁决、决策日志都放在这里。
- **调用子代理时不传 `name`**。审计员的清单原文由主会话写进调用提示词。
- **公司内容不进 claude-team 仓库**。样板、PRD、产出只在目标文档仓库和本机运行目录里。

## 步骤

### S0 准备与降级判定

**定位输入**：先看参数；没有就读当前仓库的 CLAUDE.md，再在仓库里查找。

- PRD
- 设计文档目录，以及同目录下已有的 X-NN 和 X-NN-YY 样板
- 代码目录

**格式摘要**：从样板里提取 X-NN 和 YY 两种文档的章节结构、编号与命名规则，写进运行目录，只留在本机。读不到样板时，用本目录的通用骨架，并在产出开头注明“样板未读”。

**三个降级标志**：PRD 未读、样板未读、代码未读。

- PRD 读不到属于 L2：要问用户要路径，不能硬做。如果用户坚持继续，进入**待核对模式**，不得给出“无遗漏”“覆盖完整”的结论。
- 代码读不到，YY 的动作就只精确到计划中的模块和接口，并注明“未对照代码”。

### S1 需求基线（`architect:architect` 子代理）

- 给 PRD 范围内的条目编稳定 ID。
- 建追溯表：PRD 条目 → 现有 X 文件和功能点 → YY。
- 列出实体清单，写现有设计摘要。
- 遇到歧义或冲突，用“待裁决”块返回，主会话放进问题池。

**G1 关卡**：范围内每个 PRD 条目都有 ID 和追溯状态。

### S2 三视角盲审（3 个 `team:debater` 并行，互相看不到对方的产出）

| 立场 | 清单 | 检查什么 |
|---|---|---|
| 视角审计员（覆盖） | coverage-checklist | 以 PRD 为准逐条定位遗漏；判定落点是“补本 X-NN 功能点”还是“新增 X 文件” |
| 视角审计员（闭环） | lifecycle-matrix | 资源 × 操作矩阵、状态机、横切项 |
| 视角审计员（可执行性） | executability-checklist 的 X-NN 部分 | 能不能拆成可以独立提交的 YY |

每条发现都要写明：视角键（PRD 条目 ID / 资源×操作 / 决策点）、出处、建议修法、候选修法数量，另附“清单外发现”。

### S3 交叉校验（1 轮）

- 3 名审计员各拿到全部发现（按视角键去重后的合集），逐条写“支持 / 反驳 / 补证据”。
- 同时检查别人提出的修法会不会破坏自己负责的那一维。
- 不得引入新论题；新问题放进问题池。

### S4 裁决（`team:judge`）

逐条给出结论（按 `team:deliberate` 第 6 节格式）、能否直接使用，以及落点：

- 补本 X-NN 功能点
- 新增 X 文件
- 改 YY
- 超出范围

**固定裁决规则**：

- **后端闭环是硬约束。** PRD 没写的反向操作或必检项，记为“补本 X-NN 后端功能点”，并标注“PRD 未体现”。
- **前端可以不提供**，但要写理由。
- **新增 X 文件的条件**：遗漏的是一个有独立生命周期、可以单独交付的资源，或者横跨多个 X。否则补进本 X-NN。
- 候选修法有 2 个及以上、存在实质取舍的条目，标记“需辩论”。

**G2 关卡**：每条发现都有裁决。

### S5 子辩

- S4 标记“需辩论”的条目，每条走一次 `team:deliberate` 的 T2，审计员的产出直接作为分析材料。
- 不设场次上限。
- 新增 X 文件一律走辩论。

### S6 阶段末汇总 1

- 问题池里剩下的问题按 `team:deliberate` 裁决。
- L2 一次问完，等待期间按默认值推进。

**G3 关卡**：问题池里没有“待裁决”。

### S7 写 X-NN（主会话，或交给 `writer:writer`）

- 按样板格式写；没有样板时用 xnn-skeleton。
- 必须包含：
  - PRD 追溯表
  - 生命周期矩阵：每一格写“后端提供”或“前端不提供+理由”
  - 状态机
  - 横切项
  - 子任务列表
  - “假设与裁决”小节：裁决摘要，随文档入库
  - 降级标注
- 需要新增 X 文件的，按编号规则建立骨架，并在汇报里列出。

**G4 关卡**：矩阵每一格都填了；状态机里每个非终态都有出边，所有状态都可达，没有死状态。

### S8 拆 YY（`architect:architect` 子代理）

- 每个 YY 一个文件，一个 YY = 一次独立提交。
- 按样板格式写；没有样板时用 yy-template。
- 动作写到：文件或模块、接口和字段、错误码、迁移和回滚、测试、验证命令。
- 拆分中需要做的设计选择，用“待裁决”块返回，主会话立即裁决（这类问题会阻塞下游）。

### S9 YY 可执行性复审

- 只重跑“可执行性”这一个视角，用 executability-checklist 的 YY 部分逐个 YY 检查，再由 `team:judge` 裁决。
- 不通过的回到 S8 修改；存在多个修法的走 T2。

**G5 关卡**：

- 每个 YY 的待定决策点为 0
- 每个 YY 都能独立提交、独立验证
- 矩阵每一格都映射到某个 YY，或注明“前端不提供”

### S10 交付

- 把 X-NN 和 YY 文件写进目标目录。**不提交、不推送**：用户抽检后明确说“提交”时，再按目标仓库的提交规范提交并推送。
- 按 house-rules 的格式汇报：
  - 做了什么
  - 怎么验证的：各关卡结果、覆盖计数（PRD 条目已覆盖 / 新增功能点 / 新增 X 文件）、矩阵格数、YY 数
  - 遗留问题：降级标注、待拍板清单、运行目录路径

## 编号与追溯

- 新增 X 文件，优先沿用样板仓库的编号惯例；没有惯例时，取同模块下一个未用的编号。
- YY 编号只增不重排。废弃的 YY 标“已废弃”，不删除。
- X-NN 拆分或合并后，旧编号作为别名保留在追溯表里。
