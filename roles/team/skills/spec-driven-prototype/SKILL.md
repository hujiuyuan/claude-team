# 需求文档 → 原型 + PRD 一体化

把需求文档转成一份单文件 HTML：每页上半是可点击界面原型，下半是该页的需求说明、交互流程、调整建议、变更记录、待确认项、字段与落库。同一份文件既能给客户点，也能给开发看，还能被 AI 按区域地址精确读取。

## 为什么需要纪律而不只是手艺

做原型的技术难度不高，真正会翻车的地方是**需求来源混用**。一份项目通常有多个需求文档，它们的效力完全不同：

- 一份是「全量功能愿景」，写的是这个产品最终想做成什么样
- 一份是「本期范围明细」，逐行定义了这一期到底做哪些页面、哪些字段、哪些操作
- 一份是「架构建议」，开头往往写着「可能不完善，需开发参与考虑」

如果把三份合着用，会做出一个**看起来很完整、实际上一半内容客户从没确认过**的原型。客户拿去评审时会发现里面有他没提过的功能，而真正要的功能反而漏了。这是本技能要防的第一件事。

## 主流程

### 第 0 步：先做效力排序，不要直接开始画

读完**全部**源文档后，第一件事是排效力，而不是打开编辑器。

```
1. 本期范围明细      ← 唯一的需求正文来源
2. 流程图 / 时序图    ← 流程叙述的依据
3. 全量功能愿景      ← 只用来理解上下文，不作为需求来源
4. 架构建议          ← 单独成章，明确标注非界面需求
```

判断方法：看标题和首行。写着「V1 功能架构明细」「本期范围」并且**逐行给出了字段清单与操作说明**的，是明细表。只写功能点名称、没有字段和操作说明的，是愿景表。开头自称「可能不准确」的，是建议。

把这个排序写进交付物的第一节，并立一条硬规则：

> 正文中的每一条功能需求都必须能在明细表中找到对应行号。凡是找不到出处的内容，一律归入「架构约束」或「待确认」，不混入正文。

### 第 1 步：逐行提取，建立行号映射

Excel 需求表要注意两件事：

**嵌套图片提取不到。** markitdown 之类的工具只读单元格，流程图是内嵌图片，会被整段丢掉。用 `unzip` 直接取：

```bash
unzip -j spec.xlsx "xl/drawings/media/*" -d ./media
```

取出来后**分段放大读**——流程图往往很长（如 1712×3662），整图缩略后文字不可辨，需切成 6-8 段逐段读。

**长文本列会被截断。** 读单元格时不要设 200 字符的截断，操作说明列往往有 400+ 字符，而字段定义就藏在里面。宁可分批读全，不要读半截。

提取产物是一张映射表：`页面 → 行号 → 字段清单 + 操作步骤 + 业务规则`。后面每写一条需求都标行号。

### 第 2 步：模块化构建，不要手写巨型 HTML

最终文件会到 300KB+ 上千个 DOM 节点。手工编辑必然出错、必然改崩。

拆成：底板（CSS + 渲染引擎）+ 若干页面定义模块 + 一个构建脚本拼装。改任何东西都改模块然后重新构建，不直接编辑产物。

`assets/base.html` 是可直接用的底板，含配色变量、上下分区骨架、渲染引擎（表格/详情/表单/树/时间线/卡片/图表/弹窗）、区域寻址、手风琴、表格操作列粘性。`assets/build.py` 是拼装脚本。详见 `references/prototype-architecture.md`。

### 第 3 步：每页配齐六个区域

一个页面不只是界面。**上半界面、下半文档**，文档区六块依次排开：

> **不要做成左右分栏。** 需求表格、字段表、变更记录都是宽内容，挤在侧栏里会大面积折行；而界面原型本身也要宽度。上下布局让两者都拿到全宽。并排只在两边内容都窄时才成立——这一点试过左右分栏才发现，见 `references/prototype-architecture.md`。

页面会变长，用手风琴控制：六块默认全展开，点标题栏可单独折叠，顶部给一个【全部收起 / 全部展开】。看界面时一键收起下半部分，页面立刻变短。这比把文档塞进侧栏有效得多。


| 区域 | 内容 | 来源 |
|---|---|---|
| 需求说明 | 需求来源（行号）/ 功能说明 / 页面字段 / 操作流程 / 业务规则 | 明细表逐行 |
| 交互流程 | 界面态 + 判断分支 + 字段注释 | 从操作说明推导 |
| 调整建议 | 建议 + 理由 + 影响面 + 依据 | 自己的判断，明确标注 |
| 变更记录 | 本页改动，点击定位并高亮界面区对应区块 | 修订历史 |
| 待确认 | 明细表未定义 / 定义不完整 / 两表矛盾之处 | 自动抽取 |
| 字段与落库 | 字段表 + 落库表 + 权限点 | 串起 PRD 与库表设计 |

「调整建议」宁缺勿滥。只放有明确理由和影响判断的条目，凑数的「可优化」会让人整栏都不看。没有就写「本页暂无调整建议」并说明这栏的标准。

### 第 4 步：程序化自检，不靠肉眼

产物太大，肉眼看不出问题。每次构建后跑：

```bash
node --check extracted-script.js                    # 语法
node harness.js                                     # 假 DOM 里渲染每一页
```

必查项：

- 每个导航条目都有对应页面，每个页面都有导航入口（不存在孤儿页）
- 渲染结果不含 `undefined` / `NaN`
- 所有 onclick 引用的函数都已定义
- 图表节点包围盒无重叠、无越界
- 区域地址无重复、全部符合命名规范

这套检查抓到过几个肉眼绝对发现不了的问题：122 个判断菱形因为类型判断写成 `'dec'` 而实际返回 `'d'`，全部渲染成 `undefined`；注释框没给高度导致连线坐标算出 `NaN`；金额格式化函数和弹窗构造器都叫 `M` 撞名。详见 `references/prototype-architecture.md` 的自检清单。

### 第 5 步：缺口是一等交付物

画原型的过程会逼出大量源文档没写清的地方。这些**比原型本身更值钱**——它们是客户下一次会议真正需要讨论的东西。

不要把它们埋在正文的脚注里。集中成一份清单，按对开发的阻塞程度分三级：

- **P0** 阻塞开发或影响数据模型（状态机未定义、关键字段缺失、流程断点）
- **P1** 影响功能完整性（入口缺失、规则未定义）
- **P2** 体验与细节

每条写清：缺什么、在哪一行、影响什么。给每条编号（Q1、Q2…），在原型各页引用这些编号，形成双向索引。

## 六条铁律

这几条都是踩出来的，违反任何一条都会让交付物失去可信度。

**一、每条需求可溯源。** 写进正文的东西必须能指回明细表行号。指不回的有三个去处：架构约束章、待确认清单、调整建议。没有第四个去处。

**二、源冲突不替客户选。** 发现两份文档说法不同时，采用明细表原文，并把冲突并列标出让客户拍板。哪怕你确信另一边更对——比如明细表写「微信支付/支付宝」而项目服务对象是香港机构，港式的 FPS 明显更合理——也要标出来问，不要默默改掉。默默替客户做的决定，客户永远不知道自己被决定了。

**三、不给自创内容贴来源标签。** 如果页面标题旁有「需求表·行 8」这样的溯源徽章，那自创的页面就绝对不能挂徽章。给自创内容贴假出处比自创内容本身更糟——它会让评审的人以为这块已经对齐过了。

**四、不加需求表没写的 UI 元素。** 列表页的 KPI 统计卡、详情页的额外按钮、审核页的步骤条，这些看着专业，但需求表没要求。客户会以为这些都是已确认的范围。

**五、示例数值一律标注。** 需求表通常不给具体金额、价格、配额。填进去的都是示例值，必须标「示例值，不构成已确认口径」。否则这些数字会被当成确认过的口径一路传到开发和数据库设计里。

**六、少做比多做安全。** 拿不准某块该不该做时，宁可留一个明确的「待确认」占位，也不要先做出来。删掉多做的东西要重新解释一遍为什么删，比一开始就问代价高得多。

## 配套交付物

原型之外通常还要两份：

- **独立 PRD 文件**（.md）——给不方便开 HTML 的人、走 Word 签批流程的人。内容与原型内嵌的需求说明同源，用脚本从 PRD 正文按标题层级切段生成原型内容，保证两边不会不一致。
- **数据库设计**（.md + .sql）——如果要做。见 `references/schema-design.md`。注意库表设计通常按全量口径做（含架构建议），会**大于**原型的本期口径，要在文档里显式说明差异在哪几处。

按需读取，不要一次全读：

## 素材

- `assets/base.html` — 原型底板：配色变量、上下分区骨架、渲染引擎、区域寻址、手风琴、表格操作列粘性。直接用，不要从零写 CSS。
- `assets/build.py` — 构建脚本：注入样式、拼装模块、输出产物。
- `assets/validate.js` — 自检脚本：假 DOM 渲染全页、检查导航覆盖与渲染完整性。
