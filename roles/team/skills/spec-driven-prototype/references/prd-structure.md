# PRD 的结构与写法

写 PRD 时读。目标是一份能让开发照着做、能让客户逐条确认、能被原型按页拆分嵌入的文档。

## 一、章节骨架

```
0  文档说明          依据文档与效力顺序、术语表、标注约定   ← 最重要的一节
1  产品概述          定位、本期做什么/明确不做什么、端与角色
2  核心业务流程       主线流程的文字叙述 + 差异对比
3  端 A 功能需求      逐功能点
4  端 B 功能需求
5  端 C 功能需求
6  全局规则          状态枚举、编号规则、脱敏、权限、日志、通知、定时任务
7  底层架构约束       来自架构建议文档，整章标注非界面需求
8  待确认清单         P0/P1/P2 三级
9  附录             页面清单、必须预置的基础数据、关键字段、交付物对应关系
```

**第 0 节不能省，而且必须放最前。** 它声明了哪份文档说的算、以及那条「每条需求可溯源」的硬规则。没有这一节，后面所有内容的可信度都无法判断。

## 二、功能点的统一结构

```markdown
#### 3.1.1 用户列表

**需求来源**｜机构后台明细表 行 4-7

**功能说明**

（散文，2-4 句。讲清这个功能解决什么问题、在业务链条里的位置，
不要复述字段清单——那是下一节的事）

**页面字段**

| 字段 | 说明 |
|---|---|
| 手机号 | 脱敏显示，如 138****1234 |

**操作流程**

1. 顶部筛选区提供四项条件：…点【搜索】执行筛选，点【重置】清空全部条件。
2. 【冻结】按钮仅在状态为「正常」时可用。点击弹出弹窗，必填「冻结原因」…

**业务规则**

- 冻结只影响官网登录，不影响该用户名下已生效的会籍与订单。

⚠ **待确认**：手机号脱敏格式示例「138****1234」是 11 位内地号段。
若服务对象为香港机构，港号为 8 位，脱敏规则需另定。见第 8 章 Q2。
```

六个部分固定顺序。缺哪个都行，但顺序不要变——原型按标题层级切段生成内容，顺序变了切出来的结构就乱。

## 三、功能说明怎么写才有用

**不要复述字段。** 字段清单在下一节，重复写没有信息量。

**要写这个页面的定位和边界。** 例：

> 从列表点击用户姓名或【详情】进入。这一页的定位是「查」，不是「管」——管的动作（冻结/解冻）在列表的操作列完成。页面只有三个区。

这句话让开发知道为什么详情页没有操作按钮，也让评审的人知道这不是漏了。

**约束要解释理由。** 与其只列「不可修改字段：会员号、性别、会员类型…」，不如：

> 会员号与证件号是身份识别的锚点，会员类型决定卡费，会员状态与到期时间由业务流程驱动（审核、付费、转店、续费）而非人工直改。把它们锁死可以避免台账被随手改乱。

理由能防止后续有人「顺手」放开这些字段。

## 四、六类页面的写法差异

| 类型 | 重点写什么 | 别漏什么 |
|---|---|---|
| 列表页 | 排序规则、默认条数、筛选项来源、列的特殊标记（如到期标红） | 导出是当前筛选全量还是当前页；空结果的提示 |
| 详情页 | 分区结构、哪些字段可编辑哪些只读、Tab 结构 | 不可编辑字段的变更走什么入口 |
| 审核页 | 排序（待审核置顶）、通过后的系统动作链、驳回必填原因 | 驳回原因会展示在申请人哪个页面 |
| 表单页 | 必填项、失焦校验、草稿保存、提交中禁用 | 提交后进入哪个状态、谁收到通知 |
| 配置页 | 生效时机（立即 / 需发布）、影响范围（是否影响已有数据） | 密钥类字段的加密与掩码 |
| 树形页 | 拖拽调层级、删除是否级联 | 删除后引用该节点的数据怎么处理 |

**审核页的系统动作链必须写全。** 一次「通过」往往触发四五件事：建档、生成订单、发通知、改状态、记日志。这些写在确认弹窗的文案里，而不是散在正文——因为操作者需要在点击前看到后果。

## 五、待确认的表达

正文里用 `⚠ **待确认**：…见第 8 章 QN。` 就地标注，第 8 章给完整描述。

**在功能说明里发现的矛盾要立刻标，不要攒到最后。** 例：

> ⚠ 明细表行 23 写「通过后自动创建会员档案，会员状态＝有效」，
> 但流程图与官网表行 10 写「付费到账后成为会员、建档」。
> 两者对「会籍何时生效」说法不一致——审核通过即有效，还是付费到账才有效？
> 这直接决定「到期时间」从哪天起算，也决定未付费的会员算不算有效人数。见 Q3。

三句话：**矛盾是什么**（两处原文并列）、**问题是什么**（提炼成一个可回答的问句）、**影响是什么**（为什么必须现在定）。

## 六、全局规则章的作用

把散落在各功能点的横向规则汇总，避免同一规则在多处出现不同实现。每条标出处：

```markdown
### 6.1 状态枚举

| 对象 | 状态 | 出处 | 展示 |
|---|---|---|---|
| 会员 | 有效 / 冻结 / 已转店 / 已退卡 | 行 10 | 绿 / 橙 / 灰 / 红 |
| 订单 | 待支付 / 已支付 / 已过期 / 已取消 / 已完成 | 行 107 | 彩色标签 |
```

还要有：编号规则（含唯一性作用域）、脱敏与加密、权限模型（含已明确的限制，如「变更状态仅财务及以上」）、操作日志记录点（哪些操作后要记日志，逐条标行号）、通知触发点、定时任务。

**编号规则那节通常会暴露一个大坑**：需求表往往只给示例（如「HKSA20260001」）而不给规则——前缀是否可配、序号位数、作用域是全局还是租户内还是租户内按年、是否按年重置。这几项事后极难改，必须在这一章逼出来。

## 七、与原型的同源

PRD 与原型内嵌的需求说明必须是同一份内容，靠脚本从 PRD 正文切段生成，不要手抄两遍。

```python
# 按标题层级切段
heads = [{'lv':len(m.group(1)), 'title':m.group(2), 'start':i}
         for i,ln in enumerate(lines) if (m := re.match(r'^(#{2,5}) (.+)$', ln))]
# 每个标题的正文 = 到下一个同级或更高级标题之前
# 再用 markdown 库转 HTML，映射到页面路由
MAP = [('3.1.1 用户列表','hq/users'), ('3.1.2 用户详情','hq/user-detail'), ...]
```

注意：切段时要剥掉末尾的 `---` 分隔线，否则每个功能点末尾都会多一条 `<hr>`。

## 八、附录里的一张关键表

「一期必须预置的基础数据」——这张表的价值是让客户知道**不做会怎样**：

| 类别 | 内容 | 不预置的后果 |
|---|---|---|
| 会员类型字典 | 编码 + 默认名称 | **办卡申请无法提交，整个业务卡死** |
| 默认角色与权限 | 预置角色及权限模板 | 新机构开通时后台权限一片空白 |
| 消息模板 | 各审核节点的通知模板 | 审核通过后无法发通知；某些流程直接断在这里 |
| 编号规则 | 会员号 / 订单号 / 流水号 | 无法生成业务单号 |

写「后果」比写「用途」有力得多。「办卡申请无法提交，整个业务卡死」会让客户立刻安排人去准备这份数据。
