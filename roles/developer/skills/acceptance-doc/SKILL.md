# 验收文件

被验对象：$ARGUMENTS

验收文件和设计文件一对一，只回答“怎么证明它做对了”。设计内容不复制，只引用：复制会让两处各自漂移。

## 开始前

1. 找本项目的“项目绑定”文件（先看项目 CLAUDE.md 里的指针，再找 `acceptance/` 或 `.claude/` 下的绑定文件）。字段见 `binding-template.md`。找不到就按该模板问我要，不要自己猜路径和编号。
2. 读被验的设计文件、它引用的错误码表和需求文档位置。
3. 判断触发方式（下表），不同方式“操作”和“期望”的写法不同。

## 触发方式

| 触发方式 | “操作”列写 | “期望”列能写的可观察物 |
|---|---|---|
| 外部接口 | 请求要点（哪个字段给什么值） | 状态码、错误码、响应字段、落库行、发出的事件 |
| 服务间接口 | 以调用方身份发的请求要点 | 同上，另写调用方拿到的结果是否符合约定 |
| 定时任务 | 怎么触发：等调度 / 手动触发 / 先造出满足条件的数据 | 命中了哪些行、状态怎么变、没命中的行不变、重复跑一次的结果、审计留痕、告警 |
| 消息消费 | 投递什么事件（载荷要点） | 落库行、同一条重复投递的结果、该订阅与不该订阅的事件各自的处理、失败去向 |

一份设计文件里有多个任务或消费者时，验收项表加一列“单元”，仍是一份验收文件。

## 写法规则

- “期望”只写能观察到的结果，不写“应当正确处理”这类无法判定的话。
- 覆盖：成功路径；设计里每个“不许……”各一条；接口类每个错误码各一条；定时任务要有命中、未命中边界、重复执行；消息消费要有每个订阅事件、重复投递、不订阅的事件不处理。
- 每条验收项的“出处”列指向设计文件的节或错误码表行，读的人能回查。
- 验证命令：没空跑过的如实标“未跑”，不要写得像跑通了。已有自动化测试覆盖了哪几条，读过测试代码才能填；没读过就写“未核”。
- 没有落点的内容（例如定时任务在需求文档里没有出处）按绑定文件的写法标出，不编出处。
- 不写真实口令、密钥；测试数据说明怎么造。

## 模板

```markdown
# <被验设计文件编号> · <中文名> · 验收

`<触发方式>`　`<触发一行>`

## 0 回链
设计文件路径；需求文档出处。

## 1 前置与依赖
依赖的接口、表、配置、上游事件、其它任务；测试数据怎么造。

## 2 验收项
| 编号 | 单元 | 场景 | 前置 | 操作 | 期望 | 出处 |
|---|---|---|---|---|---|---|

## 3 验证方式
命令（注明从哪个目录跑、是否已空跑）；已有自动化测试对应哪几条，没有的标“手工”。

## 4 不验什么
范围外、由别的验收文件负责的，写指针。

## 5 提交信息
一行，沿用项目的提交风格。

## 6 状态
对应设计版本；验收结论（未验 / 通过 / 不通过 原因）。
```

## 收尾自查

- [ ] 没有复制设计文件里的判定条件、字段说明
- [ ] 每个错误码或每个“不许……”都有对应验收项
- [ ] 每条验收项有出处
- [ ] 验证命令的“是否空跑”如实标注
- [ ] 路径和编号都来自项目绑定文件，不是自己猜的
