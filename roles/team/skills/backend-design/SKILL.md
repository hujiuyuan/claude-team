# 后端设计

站在后端架构师 + 高级程序员的角度设计功能，产出**给刚接手的初级程序员照着就能干**的文档。

**读者基线**（决定所有内容的深浅）：会写 Java、用过 Spring Boot、写过增删改查、看得懂 SQL；**但**没做过这个项目、不熟悉多租户、幂等、事务传播这类问题。基线内的不解释，基线外的必须解释。

## 什么时候不起这套流程

三种情况**直接回答，不产文档**：

1. **纯咨询与解释**——"这个缓存 TTL 一般设多久""事务传播行为有哪几种"。给答案就行。
2. **只读排查**——查代码为什么这么写、定位某个现象的成因，不改代码。
3. **单行修复**——改个常量、补个空判、修个错别字，且不改变对外行为。

判据一句话：**这次会不会产生「需要别人照着干」的东西？** 不会，就不起流程。

**另有一种是从中途进，不算例外**：执行手册已经写好，现在只是照着执行其中一节——**直接进步骤 10 执行期，不重跑前九步**。但一旦触发步骤 10 的「设计变更小循环」，**先补做步骤 0 的对基线**，否则手上没有基线指纹和阻碍分级的上下文，回步骤 3 是空手回。

## 产物与真理源边界

| 产物 | 装什么 | 边界（越界即错） |
|---|---|---|
| **设计文档** | 是什么 | 接口签名、字段表、建表语句**只能**写在这里 |
| **执行手册** | 按什么顺序做 | 任务顺序、改哪些文件、完成判据**只能**写在这里；出现代码块（命令行除外）即越界 |
| **未决台账** | 还没定的事，跨轮次累积 | 设计文档只留编号索引，不复述内容 |
| **需求条目表** | 要做什么、出处在哪 | 只写需求条目与来源标签，**不写技术方案**；给需求方也要看，用业务语言 |
| **校验脚本** | 锚点对账 | 放项目 `tools/` 下 |

**两份是条件产物**：未决台账在没有未决项时不建；需求条目表只在**输入是原始需求材料**（需求表、Word、口头补充）时才出——输入已是成型 PRD 的不建，见 `references/requirement-items.md`。
`S` 档只出执行手册一节。

## 速查表

**分档**——按顺序判，先命中先算，三条走完必落一档：

1. **五问全答"否"**（不新增入口 · 不动表结构 · 不改枚举值域 · 不改出参形状 · 同样的输入输出不变）
   → 跨两个以上模块？**是 → `M`**（纯重构没有结构变化，但涉及面大，要出精简设计文档兜底）；**否 → `S`**
2. **命中任一条**：新增入口 > 3 · 跨两个以上模块 · 新建表 ≥ 2 张 · 改已有枚举值域 → **`L`**
3. **其余一切** → **`M`**

`S` 只出执行手册一节 · `M` 精简设计文档 + 手册 · `L` 全套。
顺序判掉了唯一的重叠：**跨模块纯重构走第 1 条落 `M`，不落第 2 条的 `L`**。

**十一步**
`0` 备料对基线 → `1` 现状核对 → `2` PRD 取证 → `3` 阻碍分级 → `4` 循环问答 → `5` 写设计文档 → `6` 切任务 + 预检冲突 → `7` 写执行手册 → `8` 自检 → `9` 开工闸门 → `10` 执行期

**阻碍五级**
`🔴` 主线阻塞 → 停下来问，必须现在定
`🟣` 支线待定 → 问能不能候补
`🟠` 形状对不上 → 自己定处置
`🟡` 等外部件 → 逐条核实真等假等
`⚪` 口径陷阱 → 进坑清单，挂到任务上

**主线三问**——任一命中即主线；**后两问点不出具体项的，一律判支线**
① 去掉它，主流程还能从入口跑到终点吗
② 去掉它，本次功能自己产生的数据会不会错/丢/对不上账——**点名哪条数据**
③ 去掉它，本次功能自己会不会留下钱/权限/合规的敞口——**点名什么风险、谁受损**

**问人四条件**（其余一律自己定）
主线阻塞 · PRD 两处结论打架 · PRD 没写且不同取值会改数据模型或接口形状 · **PRD 写了但技术上做不到或代价不合理**

**入口六类**：HTTP · 定时任务 · 消息/事件 · 回调 · 入站远程调用 · 启动期
**十阶段**：触发 准入 **[上下文]** 入参 **[幂等]** 事务 执行 提交后 **[出口]** **[失败留痕]**
方括号四格**永远必答**，其余不适用时合并成一行写掉。

**影响面八锚点**：接口路径 · 枚举值域 · 表结构 · 出参形状 · 编号格式 · 状态机 · 事务边界 · 默认值

**通用关注点十类**（`M`/`L` 档逐类显式回答，不涉及也写「因为 X」；`S` 档只答相关的几类）：金额精度 · 时区 · 缓存 · 性能与容量 · 可观测 · 存量迁移 · 上线回滚 · API 兼容 · 限流防重放 · 消息乱序

**任务八段**：入口与作用 · 前置 · 改哪些文件 · 抄谁 · 不许碰 · 怎么做 · 本任务的坑与关注点 · 完成判据

**四种写法**：术语四列 · 坑三段（症状/原因/正确写法）· 技巧四列 · 图（单对象用流程图，多参与者用时序图且必须带失败分支）

**正文密度**：一句话删掉而不丢具体信息的，就该删。**不可压缩的是「事实」**（表格的格 · 代码块 · 有出处的原文），不是围着事实写的论述——**把一格能装下的东西另起一段再补一段推导，是最难自查的一类啰嗦**。见 `references/prose.md`。

**候补三处落地**：代码接缝（不是 `// TODO`）· 未决台账 · 设计文档留编号指针

**盲测**：写完的人判断不了够不够用。找没有上下文的人，只给真实派活的那点材料，**让他真动手写骨架**，交「卡壳清单」并标严重度。**出口判据是【会写错】级归零**，不是总数归零。做法与缺陷目录见 [blind-test.md](references/blind-test.md)。

## 三条硬规则

**1. 事实来源顺序：PRD 原件 > 代码现状 > 已有文档。**
已有文档（列注释、架构决策记录、代码注释、任务台账）与 PRD 冲突时 **PRD 赢，直接改判并记进反向同步清单，不问人**。
**纯技术任务没有 PRD，顺序整体降一档，从代码现状起**——这不是降级凑合，是这类任务的事实本来就在代码里。

**1.4 已有的东西不抄签名，只给路径。**
`grep` 得到的东西（现成的工具类、DAO、发号器、锁），文档里**只写 `包路径/文件名` + 一句话它干什么 + 「照它抄」**。
**抄签名有两个后果**：写的时候可能抄错，写对了也会随代码演进而漂。读的人能打开文件看真声明，不需要你转述。
**只有「本次要新建、代码里还没有」的接口才写全签名与字段表**——那种他确实没处查。

**判据不是「东西存不存在」，是「拿着派给他的那份材料，他能不能查到真声明」。** 查不到就必须写全值。
这条规则的整个理由是「读的人能打开文件看真声明」，**前提失效时规则就不成立**，有两种失效：

- **兄弟任务的产出还没合并** —— 路径指过去是空的，`grep` 零命中。并行派活下这是常态，不是意外
- **东西在别的模块 / 别份文档里，而派活规则不让他读** —— 打得开也不许打开

两种情况一律**在跨任务速查节里写死取值、签名、表形状**，不写指针。**指向一个他读不到的地方，比不指更糟**——
他会先去翻，翻不到再猜，白耗一轮还是猜。
⚠️ **反过来也必须做到**：任务书「改哪些文件」点名的每一个**新建件**，逐个给**类名 + 方法签名（返回类型、参数类型）+ 字段表**，**不许只写角色描述**（「注册表接口 / 生效动作接口 / 生效上下文」这种）。只写角色、不给类名签名，等于让干活人自己起名、自己定签名，而别的任务要按类名 import、按签名调用——一处对不上全线编译失败。

**1.5 数量断言要么给出查法，要么不写数字。**
「要改三处」「一共八个键」「已逐一确认没有第四处」——这类话被写错过不止一次。**要写就贴出得到这个数字的那条命令**（`grep -rln "..." 路径`），让人能自己复跑。
**「已确认没有第 N 处」比不写更害人**：它让人放弃自己复核，而它往往是错的（典型错法：grep 了路径串却没 grep 函数名）。

**2. 每条结论带证据。**
文件路径 + 行号，或 PRD 出处。写不出证据的标成"我方预设"并进未决台账。

**3. 完成判据必须可执行。**
一条能跑的命令 + 期望输出。"实现完成""功能正常"一律不算。

## 十一步

### 0 · 备料与对基线

**备料**——**什么算齐，看这次要落地什么**：

| 任务性质 | 缺什么算停工 |
|---|---|
| **要落地业务规则**（有对错之分的口径：谁能做什么、收多少钱、什么状态能转什么） | **必须有 PRD 原件，缺了直接停，不猜** |
| **纯技术任务**（重构、加缓存、补可观测、加索引、改分层、拆服务） | **没有 PRD 不算缺料**，事实来源降一档从代码现状起；但**项目约定文档缺了要停**——技术任务全靠它定规矩 |
| 两者混在一起 | 业务那部分照第一行办，技术那部分照第二行办 |

要备的料：

- PRD 原件（原型 html / 需求文档 / 需求表）——纯技术任务没有就不备
- 代码仓库（要能 grep）
- **项目自己的约定文档**（`CLAUDE.md` / `AGENTS.md` / README 的工程约定节）——**最容易漏、漏了代价最大**：该用哪个代码生成器、哪些约束有机器在守、测试命令怎么跑才不出假红、编号从哪续，全在里面。校验脚本查不出这类缺失，只能开工前读一遍
- 已有的表设计、架构决策记录、任务台账（有就给）

**先查已有的编号体系**：任务编号、台账编号、需求条目编号三类前缀，**要先 grep 项目里已在用的前缀**，且三类前缀**互不相同**，撞了就换。撞车的后果是跨文档引用全部指错地方，而且校验脚本会把需求条目编号误当成任务编号——多算或误报。三类都是 `前缀-序号` 同格式，脚本只认正则不认语义，**只有靠前缀不同才能区分**。

**对基线**——有上一轮产物就先接上：
- 读上一轮产物头部的三个指纹：PRD 的 sha256、代码仓库 commit、上一轮产物路径
- 与现值比对，有差就先列出这段时间内命中本模块的变更，再进下一步
- 术语表、坑清单、技巧表、未决台账**继承上一轮，只增补不重写**
- 上一轮未决项逐条标当前状态

**继承冲突**：要推翻上一轮某条，标 `已作废（第 N 轮）` 保留原文，另起新条，并在反向同步清单记一条"按旧口径写的代码要复查"。**不许静默改写**。

每份产物头部固定记这三个指纹。**例外：未决台账逐条记基线，不在头部记**——它跨轮次累积，多轮混在一份里，头部一个指纹说明不了任何一条是在哪个版本下判的（字段见 `references/deferral.md`）。

### 1 · 现状核对

先问代码，不问人。**不信台账摘要**——台账说没做的可能已经落地了，台账没标风险的可能缺一整块地基。去迁移脚本、枚举、类注释里验。

分两种模式：

**新建模式**——待做事项逐条核，每条给三样：现状（✅ 已完成 / 🟡 一半 / ❌ 零代码）、证据（文件路径 + 行号 + 原文引用）、还剩什么。

**改动模式**——先画出现有实现的完整链路（入口 → 调用链 → 落点），再用影响面八锚点表算**爆炸半径**；**动手前先跑通现有测试**，改完再跑一次，红了的每条都要解释是预期变更还是踩坏了。详见 `references/answer-impact-scan.md` 第五节。

**顺手登记技巧**——核代码时每遇到一个"仓库里已有的、可复用的做法"，**当场**登记一条技巧（场景 = 什么时候该复用它）。这是技巧三个来源里的第一道，形状见 `references/writing-shapes.md`。**不当场记，到步骤 8 被条数判据卡住时就只能临时编**，那正是这套流程要防的事。

输入是原始需求材料（需求表、Word、口头补充）而非成型 PRD 时，先做需求条目化并产出**需求条目表**，见 `references/requirement-items.md`。

### 2 · PRD 取证

业务口径一律从 PRD 原件取，逐字可引 + 出处。四种结果：

| 情况 | 处置 |
|---|---|
| PRD 说清了 | 直接采纳 |
| PRD 内部两处打架 | 有更高优先级规则能裁决就裁决；不能就**停下来问** |
| PRD 没写 | **先回原件确认「真没写」再处置**——作者没读到 ≠ 没写，多数口径原件里有答案。确认没写后：影响数据模型或接口形状就**停下来问**；不影响就自己定并记进未决台账 |
| PRD 写了但技术上做不到或代价不合理 | **停下来问**（详见"何时问人"） |
| 已有文档与 PRD 冲突 | PRD 赢，直接改判，记反向同步清单，**不问** |

同时扫**"产品没想清楚"的信号**，命中就默认走 🟣 候补路线而不是逼着现在拍板，见 `references/deferral.md`。

**纯技术任务本步基本空转**——没有业务口径要取。改为把项目约定文档里跟本次相关的硬约束逐条摘出来（哪些约束有机器在守、迁移号从哪续、错误码段位取哪段），它们在技术任务里起的作用等同于 PRD。问人四条件里也只剩「主线阻塞」一条适用。

### 3 · 阻碍分级

按速查表五级分。每条 🔴 之外的阻碍**必须多写一行「判错的代价」**：如果这条其实必须拍板而我自作主张定了，最坏会怎样。写不出代价的降不了级，退回 🔴。

🟣 支线待定要带五要素候补提案。主线三问与候补机制见 `references/deferral.md`。

**顺手登记坑与技巧**——⚪ 口径陷阱**当场**按三段式（症状 / 原因 / 正确写法）写进坑清单；🟠 与 ⚪ 的处置方案**当场**升格成技巧（场景 = 遇到同类形状不对时怎么办）。这是技巧的第二、第三道来源，形状见 `references/writing-shapes.md`。分完级就走、留到后面补，一定补不全。

### 4 · 循环问答

只有 🔴 中断问人，🟣 问"能不能候补"。问法与格式见"何时问人"。

拿到答复后：
1. **答复留痕**——记一行「答复内容 → 推翻了哪条既有结论 → 新引出哪些待查项」
2. **跑影响面八锚点扫描**——见 `references/answer-impact-scan.md`
3. 强制回答一次：**这个答复引入了什么现在还不存在的东西？** 答"有"就当新的待设计项，从步骤 1 完整走一遍，不许一句话带过
4. 回步骤 3 重新分级
5. **回头把分级标记改掉**——定案的 🔴 改成 ✅ 并注明「原判 🔴，某日已定案」，作废的标 ❌。**同步改的还有第 0 节的结论**（"还剩几件阻塞"那句）与执行手册的开工闸门。
   ⚠️ **这一步最容易漏**：台账更新了、正文写了定案小节，唯独标题上那个 🔴 和首屏结论没动，于是文档看起来永远卡着。判据：**扫一遍全文的 🔴，每一个都要么真的还在阻塞、要么已经改成 ✅**。
   **不静默改写**：原判要留着（写成「原判 🔴 主线阻塞」），后来的人才看得出「当时为什么卡、后来怎么解的」。

**收敛判据**：连续两轮扫描零新增，才算收敛。
**出口**：同一个问题三轮问答仍不收敛，强制降级——转 🟣 候补，或标"带假设推进"并把假设原文写进设计文档显眼处。**不许无限循环。**

### 5 · 写设计文档

骨架与每节纪律见 `references/design-doc.md`。设计正文第一节是**入口与生命周期**，见 `references/entry-points.md`。

### 6 · 切任务 + 预检冲突扫描

切任务三判据、主线优先排序、预检冲突扫描的做法全在 `references/exec-manual.md` 第一、二节。三件事的**卡口**是：

- 切不出**独立完成判据**（一条能跑的命令）的切法就是错的——判据跟上一个任务重复说明切太小，一条命令验不完说明切太大
- 每批要标注**这批做完主流程能不能端到端跑通一次**——标不出来说明没按主线优先排
- 同批可并行的任务必须两两比对共享文件 / 接口 / 枚举，冲突**预先裁定**写进手册首屏，不留给执行时现场协调

**回填设计文档**：任务切完后回头补上设计文档第 8 节「任务索引」（`| 设计小节 | 由哪个任务落地 |`）。**这一节在步骤 5 写不了**——那时任务还没切出来。不回填，自检里「两份文档的任务编号集合相等」永远过不了。

### 7 · 写执行手册

每任务八段。见 `references/exec-manual.md`。

### 8 · 自检

逐条勾，缺一项不算过：

- [ ] **孤儿检查**：每个新增的类、方法、表、枚举，都能从六类入口里的至少一个追到。追不到的补入口或删掉
- [ ] **反向警戒**：新增了一堆 service 和 DAO 却一个新入口都没有 → 一定有问题
- [ ] 每类涉及的入口，第 3/5/9/10 四格必答无空（`M`/`L` 写在设计文档 4.0；`S` 档写在执行手册该任务第 1 段「入口与作用」里）
- [ ] 每条 🟣 有完整五要素候补提案
- [ ] 每条非 🔴 阻碍有「判错的代价」
- [ ] 技巧条数 ≥ 坑条数的一半，且每条技巧的「场景」列能指回具体代码位置或阻碍编号（两张表在设计文档第 7 节；`S` 档在执行手册全局章节）
- [ ] 两份文档的任务编号集合相等（**`S` 档免**——只有手册一份，无从比对）
- [ ] 执行手册里没有代码块（命令行除外）
- [ ] 数字没写死（条数、任务数写"以下表实际行数为准"）
- [ ] **分级标记与实际状态一致**：全文每个 🔴 要么真的还在阻塞、要么已改成 ✅ 并注明原判；第 0 节结论里"还剩几件阻塞"那句与实际相符；执行手册开工闸门的勾选状态同步
- [ ] **通用关注点按档回答**——`M`/`L` 档十类全答（金额精度 / 时区 / 缓存 / 性能与容量 / 可观测 / 存量迁移 / 上线回滚 / API 兼容 / 限流防重放 / 消息乱序），不涉及也写「本次不涉及，因为 X」，无空；`S` 档不出设计文档，只在执行手册该任务第 7 段「本任务的坑与关注点」里答**跟本次改动直接相关的那几类**
- [ ] **密度抽检**——两道都过：禁用语 `grep` 零命中 + 删句抽检（`L` 抽三段 / `M` 两段 / `S` 一段，一句都删不掉才算过）。做法与禁用语命令见 [prose.md](references/prose.md)。🔴 **必须排在盲测之前跑完并改完**——盲测一开跑文档就冻结，那之后改措辞会让报告指向已不存在的文本
- [ ] **工序落点反查（元检查）**——把 `references/` 逐个文件过一遍，每个文件问两句：它定义的**每道工序**，本次有没有真的执行并留下产出？它定义的**每张表 / 每份清单**（术语表 · 坑清单 · 技巧表 · 入口十阶段 · 通用关注点 · 反查链 · 未决台账 · 需求条目表），在本次产物里有没有一处收留它？任一答"否"就是漏了落点，补上
- [ ] 校验脚本全绿（12 项：路径 · 标识符 · 任务编号 · 台账 · 手册越界 · **小节指向** · **字段表第一列与类型** · **库表列** · **命名长度** · **签名走样** · **清单闭包** · **术语表**）。术语表那项判失败的是「收了没用到 / 回指指不到 / 「不是什么」列空着」三条；它同时会列出「正文加粗但没收录」的候选，**那部分不算失败，人工过一遍决定收不收**
- [ ] **盲测抽检**通过——**开干净子代理跑，不问用户**；出口判据是**【会写错】级卡壳归零 + 矛盾归零**，不是「跑过一轮就算」（`L` 档抽 3~4 个任务，`M` 档抽 1 个，`S` 档免）

**盲测抽检——必做，不问，直接派子代理跑。** 完整做法与缺陷目录见 [blind-test.md](references/blind-test.md)。

**四条不许违反的**：

1. **自评零信息量。** 刚写完全文的人「假装看不见」做不到——**没开干净子会话就是没做**，不许勾这一项，也不许拿「人过目那一关兜底」当替代。
2. **不问用户，直接跑。** 这是自检的一部分，不是需要授权的动作。派几个子代理，材料范围严格照真实派活给。
3. 🔴 **跑之前冻结文档，跑完再改。** 中途改会让报告指向已经不存在的文本，那一份就废了——**这是真犯过的错**。
4. **出口判据是【会写错】级卡壳归零 + 矛盾归零**，不是「跑过一轮就算」。只剩【只是不确定】才算过。

**收敛判据——看的是「同一批问题有没有消失」，不是光看条数。**

每轮把【会写错】逐条记下来，下一轮回来先做一件事：**逐条比对，上一轮那几条还在不在。**

| 情况 | 判定 | 怎么办 |
|---|---|---|
| 上一轮的都没了，冒出**新的几条** | ✅ **在收敛**——修掉一层露出下一层，正常 | 继续修继续跑 |
| 条数降了 | ✅ 在收敛 | 继续 |
| **上一轮那几条原样还在** | ❌ **没修对**，不是没修够 | 回头看那几条到底为什么没被修掉，别急着跑下一轮 |
| 连续两轮**既没减少、也没换批** | ❌ 不是措辞问题 | 回步骤 6 **重切任务**，不许继续磨措辞 |

⚠️ **光看条数会误判**：真实项目里出现过某个任务连续两轮都是 2 条，但**是两批完全不同的问题**——那是在收敛，不是卡住了。

**最高频的那一类，写文档时就要防**：跨任务共用的接口签名散在各任务书里，而派活规则不让读别人的任务书 → **设计文档必须单开一节「跨任务接口速查」**，每个任务书都点名它。

这一节有两条硬约束，**违反哪条都会让整节失效**：

1. **不许出现指向「不在任何任务可读清单里」的小节。** 「类名见 §4.2.1」而 §4.2.1 不在清单里 ＝ 把答案锁进保险柜再把钥匙收走。
2. **装的不只是方法签名，还有枚举的全部取值、错误码段位起点、别的任务要建的表的列清单、跨模块要调的接口。**
   只装方法签名是最常见的漏法——实测某条线连续两轮的「会写错」里，枚举取值拿不到占了一多半，而速查节当时「有」，只是没装枚举。

### 9 · 开工闸门

全过才准写第一行代码：

- [ ] 🔴 阻碍清零
- [ ] 🟣 全部有明确处置（已候补或已定），没有悬空的
- [ ] 连续两轮影响面扫描零新增
- [ ] 每个任务的完成判据都是一条能跑的命令
- [ ] 步骤 8 自检全过（**含盲测真的开子代理跑过、且【会写错】已归零**）
- [ ] **人过目**：设计文档与执行手册交给人确认过（`L` 档必须，`M` 档建议，`S` 档免）。前五项全是自检与机器判，**这一项是唯一的人工闸门**——交出去的时候直接说「这两份看一下，没问题我就开工」，别只丢路径

### 10 · 执行期

- **一任务 = 一 PR = 一会话。** 派活时把「执行手册那一节 + 设计文档被它指到的小节 + 全局红线」一起发出去，**不发标题**
- **销号**：做完在手册那一节标 ✅ 并附证据（PR 链接 / 命令输出）
- **设计变更小循环**：干到一半发现设计错了 → 停手 → 回步骤 3 重新分级 → 是 🔴 就问人 → 回灌 → 跑影响面扫描 → 更新两份文档 → 才继续写代码。**禁止就地改代码不回灌**
- **完工验收**：全部任务销号后跑一次 `--strict`，源码里找不到的标识符 / 路径 / 台账接缝此时算失败，逐条销掉或回灌。**没跑 `--strict` 不叫完工。**

```bash
python3 tools/check-anchors.py --src . --design d.md --manual m.md --ledger l.md --strict --task-pattern '本项目的任务编号正则' --ledger-pattern '本项目的台账编号正则'
```

  **两个 pattern 必须显式给，且收窄到各自前缀**（如 `T-\d{2}`，不是 `[A-Z]{1,4}-\d{1,3}`）——宽正则会把手册里引用的需求条目编号误算成任务。没传参数时 `--strict` 会报「一条编号都没匹配到」而不是静默放行，别改正则去糊弄它。脚本输出的「前缀分布」是兜底：混进外来前缀一眼能看见。

## 何时问人

只有这四种，其余（技术选型、命名、分层、能从代码查证的现状、已有文档与 PRD 的冲突）一律自己定。

⚠️ **升级问人 / 记未决台账之前，先穷尽 PRD 原件自查。**「PRD 没写」是必须验证的结论，不是默认假设——**作者没读到 ≠ 没写**，把「没读到」升级成「问人」等于让用户替你查 PRD，来回白耗 token。下「没写」这个结论前先回原件查，并留痕（查了哪页 / 哪条，结果是什么），**查不到才升级**。没有这份留痕的「PRD 没写」不算数。

| 条件 | 问法必须带 |
|---|---|
| **主线阻塞** | 事实原文 + 出处 / 不定的后果 / 2~3 个选项及各自代价 / 推荐项 |
| **PRD 两处打架** | 两处原文并列引出 + 各自出处 / 推荐采信哪一处及理由 |
| **PRD 没写**且影响数据模型或接口形状（**已回原件确认过真没写**）| 空白在哪 / 不同取值分别导致什么 / 建议默认值及理由 |
| **PRD 写了但技术上做不到或代价不合理** | PRD 原话 + 出处 / 技术上为什么难 / **代价数字**（多几天、慢多少倍、多几台机器）/ 一个"改一点点就能做"的替代方案 |

🟣 支线待定走**另一条问法**——问的是"能不能候补"，不是"选哪个"，五要素见 `references/deferral.md`。

**给需求方看的内容用业务语言**：写"会籍到期后还能不能续、宽限多久"，不写"某字段的某个属性"。
