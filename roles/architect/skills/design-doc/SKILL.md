# 技术方案文档

主题：$ARGUMENTS

按下面的结构输出。小需求可以合并或省略章节，但“推荐方案”“风险”“验证”不能省。

```markdown
# <标题>

## 结论
推荐方案一句话 + 最关键的一条理由。需要我拍板的点列在这里。

## 背景与目标
- 为什么要做（问题或机会）
- 目标：可衡量的验收标准
- 不做什么：明确排除的范围

## 现状
相关模块、数据流、约束（引用文件路径）。只写和本方案有关的。

## 方案对比
| 维度 | 方案 A | 方案 B |
|---|---|---|
| 思路 | | |
| 改动范围 | | |
| 复杂度 / 工作量 | | |
| 风险 | | |
| 可回退性 | | |

## 推荐方案
- 关键设计：接口、数据结构、模块划分、调用流程（必要时用 mermaid 图）
- 兼容性与迁移：旧数据、旧接口、配置怎么过渡
- 回滚方案：出问题时怎么退回

## 风险与未知点
每条写：风险是什么、发生概率与影响、怎么提前验证或缓解。

## 验证
怎么证明做对了：测试策略、指标、灰度或试运行方式。

## 任务拆解
（按 task-breakdown 技能输出，或链接到拆解结果）
```

## 写法要求

- 方案对比要真实：不要为了衬托推荐方案而写一个稻草人方案。
- 每个技术事实都要能追溯到代码、文档或实测；查不到就标注“未验证”。
- 用具体数字代替形容词（“p99 从 800ms 降到 200ms”，而不是“显著提升性能”）。
