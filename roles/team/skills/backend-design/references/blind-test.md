# 盲测：唯一能证明「新人照着能写」的办法

**写完文档的人，判断不了这份文档够不够用。** 你脑子里装着上下文，看到「照 X 抄」会自动补全成「哦就是那个类那个方法」，而新人补不出来。**自评「我觉得写清楚了」零信息量。**

**盲测就是找一个真的没有上下文的人，只给他能拿到的那点材料，看他能不能写出来。**

---

## 怎么跑

### 1. 材料范围要跟真实派活完全一致

真实派活给的是「**执行手册里他那一节 + 设计文档里那一节点名的小节 + 文末红线自检表**」。盲测就给这些，一个字不多。

**必须明令禁止的**（不禁就一定会被读到，结果作废）：
- 你自己的工作目录（研究文件、台账、裁定记录）——那里全是答案
- 上一轮盲测的报告
- 手册里**其他任务**的章节
- 设计文档里**没被点名**的小节
- 需求原件（真实派活时新人也不读它）

⚠️ **连「为了定位行号而读文件前 100 行」都要禁**——手册开头往往有开工闸门、批次表、冲突裁定，那些是派活人看的，不是干活人看的。要求用 `grep -n "^### 任务号"` 定位再 `sed` 切片。

### 2. 必须让他**真的动手写代码**

只让他「读一遍说说看懂没有」，得到的一定是「看懂了」。**要求写出骨架**：接口、全部出入参类型、实现骨架，**签名完整、每个字段有名有类型**，方法体可以是注释。

写到一个隔离目录，**不许碰真实源码树**。

**动手才会暴露问题**——「这个字段叫什么」「这个方法返回什么」，读的时候能糊弄过去，写的时候糊弄不过去。

### 3. 报告要「卡壳清单」，不要「意见」

每处「不得不猜」的地方，逐条：

```
- 严重度：【会写错】或【只是不确定】
- 卡在哪：
- 文档原话：（要引原文，不许转述）
- 为什么这句话不够我写代码：
- 我猜了什么：
- 猜错的后果：
```

**两条纪律**：
- **「我最后还是想办法写出来了」不是不写的理由**——「想办法」本身就是文档没说清的证据。
- **必须标严重度。**【会写错】= 猜错了代码就是错的、或者跟别人对接不上；【只是不确定】= 两种写法都能跑通，只是风格。**收敛看的是【会写错】那一档归零，不是总数归零**——总数永远不会归零，总有人对命名有想法。

### 4. 并行跑多个任务，不要只跑一个

不同任务暴露的缺陷类型不一样。挑：**改动最大的**、**上一轮判「不能」的**、**卡壳最多的**、**跟已有前端/上游代码有契约的**。

---

## 出口判据

**【会写错】级卡壳归零，且矛盾归零** → 过。
只剩【只是不确定】→ 过，那些记进台账即可。
**还有【会写错】→ 修完再跑一轮。** 别在「差不多了」的感觉上停。

---

## 缺陷目录：真实盲测里反复出现的缺陷类型（按 A~H 八类分组）

写文档时**逐条自查**。这不是理论清单，每一条都是真的把人卡住过。

### A 类 · 字段表

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| A1 | 字段表**只给中文名**（「订单号」「费用项目名」），不给**真实的 JSON 键名 / Java 字段名** | 前端做穷尽校验时键名对不上，**整单作废**，而且失败是静默的 |
| A2 | 字段类型写成「**A 或 B**」（如「字符串 或 键值对」） | 强类型语言里一个字段不能是两种类型，写代码的人必须自己发明一个形状 |
| A3 | 「**完整 DDL / 完整字段见另一份文档**」，而那份文档**不在这个任务的可读范围内** | 把答案分流到了看不见的地方，等于没写 |
| A4 | 只给**概念列**（这张表要能存"进来时的状态"），不给**列名、类型、可空** | 建表时每个人拼一套不同的列名 |
| A5 | 表里的字段和业务规则**数量对不上**（业务说「附件是数组、至少一张」，建表却给了单数的两列） | 自相矛盾，只能自己选一个解，选错了整个建模假设就错了 |
| **A6** | **枚举 / 封闭值集合只给中文名和值，不给 Java 类名**（「订单类型」「钱流」给了值 `member_fee`/`F2`，但类名 `OrderType`/`MoneyFlow` 一个字没有）| 下游要写字段类型、要 `switch` 判值，只能猜类名——**跟 A1 是同一类病**：第一列 / 类名必须是代码里真实的名字 |
| **A7** | **封闭类型声明的「N 种结果」与实际状态分支「N+1 种」对不上**（说「返回四种结果 + 四个 record」，前置状态表却有第五种「订单状态不接受入账」）| 照「四个 record」写，第五种分支无处编码。**数清楚分支：要么归并进一个带 `reason` 的档，要么老实写 N+1 个** |

**硬规则：出入参表的第一列必须是「代码里真实的名字」，中文只能出现在「含义」列。** 类型必须是单一确定类型；表达不了的用封闭类型（sealed）把互斥性交给编译器，而不是写成「或」。

### B 类 · 指向

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| B1 | 写「见 §X 那几张表」，而 §X 里**那些表根本不存在** | **比不指还糟**——明确告诉他别看这个要看那个，那个是空的 |
| B2 | 数量断言（「要改三处」「八个键」）与实际**不符** | — |
| B3 | 写「**已逐一确认，没有第四处**」这种**未经充分验证的断言** | 比不写更害人，它让人放弃自己复核。**要写就写清查法**（贴出那条 grep 命令），让人能自己复跑 |
| B4 | 任务书点名的小节**只是索引**，正文在另一节，**而那一节没被点名** | 干活的人按派活规则读不到正文，等于指了个空 |
| **B5** | **跨任务共用的接口签名散在各任务书里**，而派活规则不让读别人的任务书 | **这是最高频的一类**——他只能猜方法名、猜参数、猜返回值。**解法：设计文档单开一节「跨任务共用的接口速查」，把所有任务间调用的签名集中一处** |
| **B6** | 建了速查节，**却只给方法签名不给字段清单**，详细的在别的小节而任务书没点名 | **B5 修一半的样子**——他知道调哪个方法了，还是不知道要填哪些字段。速查表**每一行都要标「详细字段表在哪一节」**，且**任务书要把那些小节一并点名** |
| **B7** | 任务书的指针**只指了一节**（「先读 §X」），而他实际要读五六节 | 同上。**每个任务书要把它实际要读的小节全列出来**，不是给一个入口让他自己找 |
| **B8** | 写「照 `任务 X` 的某某抄」，而**任务 X 的章节按派活规则读不到** | 等于没说。**要么直接描述形状，要么指向设计文档里的小节** |
| **B9** | 任务书**「2 前置」清单之外的正文**（第 3/4/6/7 段）里的「见 §X」读指引指针，没算进清单闭包——正文三次写「三条规矩见 §4.3.0」，而 §4.3.0 不在清单 | 干活人被正文指引去读，却按派活规则读不到。**清单闭包要扫「任务书整节正文」的读指引指针，不只扫清单里的小节** |
| **B10** | **跨任务接口「压根没设计」**——不是签名散落（B5）、不是签名编错（C0），而是这个接口从**字段形状到方法签名到批次依赖都没定**（例：第 3 批的任务要调第 5 批任务建的表，表又按另一种场景设计装不下）| 比 B5/C0 更严重——散落还能找、编错还能核，**压根没设计就只能在文档里假装有**。发现信号：某任务要「落进 / 调」一个别的任务建的件，但速查节只给了类名没给方法签名，且完成判据没测这个动作 |
| **B11** | **通用模板句无脑贴进每个任务书**——「你要调的别人接口，签名一律去 §4.3.5 查」这句，落在一个「只定义接口、不调别人」的任务上（例：ENG-04 建注册表，本就不调任何业务接口）| 干活人被一句「去读清单外的一节」误导，而那一节对他根本没用。**模板句要按任务性质区分**：定义接口的任务写「你的签名已定在 §X」，调别人接口的任务才写「去 §4.3.5 查」 |

**硬规则：任何「共 N 处 / 一共 N 个」的断言，要么贴出得到这个数字的命令，要么不写数字。**

### C 类 · 与既有资产核对

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| C1 | 没核对**已经写好的上下游代码**的契约——路径、字段名、**返回体的包装形状** | 后端上线，前端每次成功请求都报「失效」 |
| C2 | 让人**新建一个仓库里已经有的东西**（接缝、发号方法、锁位登记） | 撞车，而且往往直接违反「一件事只有一处实现」这类红线 |
| C3 | 引用的**库表列根本不存在** | 写到一半才发现没法取值 |
| C4 | 设计里说「从 X 拷入 / 由 X 维护」，而 **X 在库里没有落点** | 同上 |
| **C5** | 写「**照 X 抄**」时，对 **X 的形状描述错了**——（例：写「`int updateWithVersion` 照 `ApplicationDaoImpl` 抄」，但 `ApplicationDaoImpl` 真实是 `void`+冲突抛异常，不是返回 `int`）| **签名走样检查抓不到**——它比对的是「文档里的签名对象」，而签名对象（新件）不存在时就被跳过，**没人去比对「被抄对象 X」的真实形状**。规则：**「照 X 抄」旁边必须核过 X 的真实签名，抄的是哪一面、返回什么、怎么报错，一字不差** |
| **C6** | 写「**照 X 抄**」，但 **X 压根不具备要抄的那个机制**——（例：写「照 `PermRegistry` 抄『启动时装好、运行期只读』」，可 `PermRegistry` 是**静态常量类**、`private PermRegistry()` + 编译期写死的内联 Map，**没有 bean、没有启动钩子**，照它抄不出「启动期注册」的落地机制）| 读者只能抄到一句口号，抄不到实现。**「照 X 抄」前先确认 X 的形态真的具备要抄的能力**：是静态常量类还是 bean？有没有钩子？没有就只抄语义、另指一个真机制 |

### 🔴 C0 · 最容易在「唯一真理源」那一节犯的错：**凭印象编签名**

写「跨任务接口速查」这种被当成真理源的地方时，**每一个方法签名、每一个包路径、每一个类名，都必须打开真实代码核过再写**。

真实案例：写「照抄现成的那个方法」时，**同一行里给出的签名却是编的**——真实是 `UUID openXxx(UUID, UUID, Map<String,Object>, String)`，写成了 `void openXxx(UUID, UUID, String, String)`，返回值和参数类型都错，包路径也从 `dao/` 写成了 `service/`。

**后果比普通错误严重得多**：别人会照着这张表写调用代码，签名错一个字，下游几个任务全编译不过——而且他们会以为是自己写错了。

**规则：速查表里出现的每一个签名，旁边要能说出「我在哪个文件第几行看到的」。说不出就别写。**

**硬规则四条**：
1. **动手写任何「接缝 / 假件 / 发号方法 / 恒放行实现」之前，先搜仓库有没有同义的件。**
2. **凡是有前端/上游已经写好的接口，逐字段核对契约**，包括返回体外层包装的形状与字段名——这一条最容易漏，因为它不在任何一份设计文档里，只在两边的代码里。
3. **文档里提到的每一个库表列，都要在迁移脚本里 grep 一遍确认存在。**
4. **文档里给出的每一个方法签名 / 类名 / 包路径，都要打开真实文件核过**（见上面的 C0）。

### D 类 · 从列注释里抽事实

**列注释是本项目信息密度最高的地方，而且经常是唯一权威。逐列读，别扫。**

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| D1 | 列注释里的**单位 / 语义**没被抽出来（「费率，**百分比数值**（0.6 表示 0.6%）」） | 算错 100 倍，**而且不抛任何异常** |
| D2 | 文档写的**枚举取值**跟列注释的值域**对不上** | 落库的值数据库注释根本不认 |
| D3 | **`NOT NULL` 约束没被检查**——某几条入口根本没有值可填 | 插不进去，而且是运行时才发现 |
| D4 | 列注释说「由 X 自己维护」，**没去查 X 在哪** | 写到那一列时无值可取 |
| D5 | 列注释里的**反向警告**（「不要照 Y 写」「合成一列就等于把某道防线作废」）没被带进文档 | 后人重新踩一遍 |
| **D6** | **同一个概念在不同层用了不同的字面值**，文档只写了其中一个（例：跨天判定，SQL 层写 `'Asia/Hong_Kong'`，Java 层的常量却是 `Asia/Shanghai`——同一个时区两个名字）| 照文档在 Java 里手写另一层那个字面量，**行为上碰巧也对，但违反了「一律用常量」的规矩，下次真要改时会漏掉这一处**。要**两层都写出来，并说明为什么不统一** |
| **D7** | 说了「列清单已给全」，又说「照某张表抄」，而那张表有**横切列**（主键 / 租户 / 创建时刻 / 排障号）不在你的清单里 | 读的人不知道抄过来的那几列是该留还是该删。**要说清「给全」指的是业务列，横切列照通用约定走** |

### E 类 · 分支完整性

| # | 缺陷长什么样 |
|---|---|
| E1 | 校验有四项，**只写了其中一项**不通过时怎么办 |
| E2 | 状态守卫**只写了部分状态**，剩下的进来怎么办没说 |
| E3 | 有成功和失败两个分支，**只写了失败分支**要做的事，没说成功分支要不要做同样的事 |
| E4 | 有「上限 / 阈值」，**没说 0 是什么意思**（不限？一次都不许？） |
| E5 | **两个可配置维度交叉时，没说清哪些组合根本不成立。** 例：发起形态有四种、结果剧本有五种，但「同步出结果」那种形态天生没有回调，「超时不回调」「重复回调」两档在它下面不成立——不写清楚，验收用例里有两条根本写不出来 |
| E6 | 引用了仓库的**命名/长度硬规则**却自己违反（例：给出的测试方法名超过了 `README` 规定的长度上限） |

**硬规则：凡是列举（N 项校验、M 个状态、两个分支），必须逐项给出处置，不许只写「典型的那个」。**

### F 类 · 机制

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| F1 | 「建记录 + 抛异常」写在**同一个事务**里 | 互相抵消——抛异常回滚会把刚建的记录一起干掉，而验收判据要求那条记录存在 |
| F2 | 说了「要幂等」，**没说用什么机制** | 数据库没有唯一索引兜底时，裸的「先查后插」并发下会写两行 |
| F3 | 「走事务提交后的钩子」，**没说这个钩子怎么写**，尤其是钩子里还要写受行级安全保护的表时 | — |

### G 类 · 措辞

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| G1 | 「**前置：X 已合并**」被读成「仓库里现在已经有了」 | 新人去 grep，grep 不到，当成文档错误报上来。**要写明这讲的是开工顺序** |
| **G8** | 「已合并＝开工顺序」这条说明**写在了派活规则禁止读的位置**（如手册第 0 节开工闸门，而派活规则只让干活人读「他那一段 + 点名的小节」） | **说明等于没写**——干活人读不到，照样误解。**规则「知道了」还不够，要落在干活人读得到的地方**：要么每个任务的「2 前置」里带一句，要么「已合并」这个词本身改成「开工顺序：X 先于 Y」 |
| G2 | 用「**日期**」「**天数**」这类词，而实际口径是**精确时点 / 精确时长** | 同一天内的边界情况算出来不一样 |
| G3 | 「照 X 抄」，而 X 的**用法跟你以为的不一样**（比如那个工具类全仓只有一处注入，业务端点根本不该直接用它） | 照字面做就是错的。**「照 X 抄」必须说清抄它的哪一面** |
| G4 | 只给了**中文档位名**（「待审核 / 已通过 / 已驳回」），没给**机器可读的取值** | 查询参数、枚举码到底传什么，只能猜 |
| G5 | 写「不晚于今天」「当天」这类词，**没说「今天」按哪个时区算**，或者只说了时区名却没说**用哪个常量** | 跨时区边界行为不一致；写了字面量则违反「一律用常量」的规矩 |
| **G7** | 文案里写「带两个占位：A、B」，而紧跟着的**例句词序是 B、A** | 占位顺序错了，线上文案会把两个数字说反 |
| **G6** | **要求做某件事，却跟仓库里那个组件写死的架构前提冲突**（例：要求「按令牌限流」，而现成限流组件的类注释写着「计数键绝不含任何请求体内容」） | 照做就是违反那条注释；不照做又不符合任务书。**必须自己先撞一次，给出处置** |

### H 类 · 时序与顺序

| # | 缺陷长什么样 | 后果 |
|---|---|---|
| H1 | **步骤顺序与表的写入纪律冲突**（例：把「落记录」排在「校验」前面，而那张表「只增不改」——那就必须先校验完再落一次写对） | 照字面顺序写不出来 |
| H2 | **上下文的设置时机写反**（例：写「进事务后设租户值」，而写数据库会话变量的钩子是开事务那一刻调的） | **静默查不到任何数据**，不报错，极难定位 |
| **H3** | **边界改判注（顶部 🔺 警告）与正文打架**——注里说「正文尚未按新边界重写，照旧文开工会白做」，正文却**还是旧文**，还把重写推迟给另一个任务（「等 X 落地时重写」） | 干活人要么照注（白做）、要么照正文（撞约束），两头都不对。**纯 AI 项目里「等 X 落地时重写」＝ X 不派就永远是旧文**。规则：**拍板后当场改正文**，哪怕改成「调 X 服务（签名待定，见台账）」；不许留一个「看起来还能照抄」的旧文 |

## 为什么补了三轮还在出问题——一次真实的复盘

真实项目跑了四轮盲测，数字是这样的：

| 轮次 | 卡壳 / 会写错 | **自相矛盾** |
|---|---|---|
| 第 2 轮 | 43 | 18 |
| 第 3 轮 | 19 | 11 |
| 第 4 轮 | **15** | **16** ← 反弹 |

**卡壳一直在降，矛盾降到 11 之后反弹了。** 这两个数字的含义不一样：

- **卡壳 = 我没写**。补文字就能降，所以它单调下降。
- **矛盾 = 我写错了**。而**修复本身就是在写新文字，新文字同样没经过验证**——所以每一轮修复都在以差不多的速率注入新的错误。

第四轮那批矛盾里，**有一半直接来自第三轮的修复动作**：新加的「跨任务速查」节里编错了一个方法签名、「六张表」标签下列了七个、新挂的指针只指一节而实际要读五六节。

**结论：用「写更多文字」去修「文字写错了」，不会收敛。**

### 两条从这次复盘里长出来的规则

**一、可机械验证的，必须机械验证，不能靠「记得核实」。**
原来的检查全是**存在性检查**（路径在不在、标识符有没有、小节在不在）。那抓不到「东西存在，但你对它的描述是错的」——类和方法都在，只有签名是编的，所有检查都过。
**所以加了签名走样检查**：把文档里写的方法签名跟仓库里真实的那一个逐个比参数类型与返回类型。

**二、能不抄就别抄**（见 [design-doc.md](design-doc.md) 那条「已有的东西不抄签名」）。
文档里每复制一条代码里已有的事实，就多一个会写错、会漂移的点。**`grep` 得到的东西给路径，让读的人去看真声明。**

### 什么时候该停止打补丁

**连续两轮矛盾数不降**，说明问题不在个别措辞，在于**文档已经大到无法保证内部一致**。
这时候不要再补，改做**一致性整理**：把重复陈述同一事实的地方合并成一处、把「已有的东西」的签名换成路径、把索引节与正文节合并。**补丁只会让它更大。**

### 修一处漏一处——修复动作本身也要盲测

真实案例：某轮盲测报「枚举只给中文名不给类名」，修的时候给速查节补了**类名**，下一轮换个任务盲测，报「枚举**码值**拿不到」——因为上一轮补的是「这个任务卡在类名」，补的也是类名；而另一个任务要的是**码值**（注册表键），码值还在禁读的 §4.2.1 里。

**教训：修缺陷时，针对的是「上一轮那个任务的具体卡壳」，不是「这一类缺陷的系统性消除」。** 修完要自问一句：**这个缺陷还有没有别的任务会换个角度踩？** 枚举类名补了，那枚举码值呢？「照 X 抄」的 X 形状核了，那 X 的报错方式呢？

**这条没法机械检查，只能靠：修完一类缺陷，把「同类的所有任务」在脑子里扫一遍，而不是只扫报出它的那一个任务。**

## 最后一条

**这份目录是活的。每跑一轮盲测，把新出现的缺陷类型补进来。**

如果同一类缺陷第二轮还在出现，说明**规则没写进这份文件，或者写了但自查时跳过了**——那是流程问题，不是运气问题。
