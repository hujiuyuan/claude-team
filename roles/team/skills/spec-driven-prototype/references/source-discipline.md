# 多源需求的效力判定与缺口处理

开工前必读。本文档解决的是「哪份文档说的算」这个问题。

## 一、为什么这是最容易翻车的地方

一个项目的需求通常不止一份文档，而它们的效力天差地别。常见组合：

| 文档特征 | 实际性质 | 效力 |
|---|---|---|
| 标题含「V1 / 本期 / 一期功能架构明细」，**逐行给出字段清单与操作说明** | 本期范围的权威定义 | 唯一的需求正文来源 |
| 只列功能点名称，没有字段与操作说明，首行写「XX 使用」 | 全量功能愿景 | 只用于理解上下文 |
| 开头自称「可能不完善不准确，需开发参与考虑」 | 架构建议 | 单独成章，非界面需求 |
| 流程图 / 时序图 | 流程叙述依据 | 用于写流程章节 |
| 账号体系 / 权限体系等专题文档 | 跨模块约束 | 与明细表冲突时需拍板 |

**判断方法**：看有没有「字段清单」和「操作步骤」。有的是明细，没有的是愿景。愿景表看起来更全，正是它的危险之处——它会让你做出一个客户从没确认过的完整系统。

## 二、混用的典型症状

以下都是真实发生过的：

- 用户详情页需求只要求 3 个区域 9 个信息点，实际做成了 20 多个。多出来的「重置密码」「操作日志」全部来自愿景表。
- 明细表明确写「冻结按钮在**用户列表的操作列**」，实际把按钮放到了详情页。
- 表单配置页做了完整的「字段映射到 person.name」机制——那是架构建议里的内容，明细表只要求「模板列表 + 创建 + 编辑 + 预览 + 复制 + 停用」。
- 子机构模块实际只有 5 个，做成了 7 个，多出来的两个凭想象补的。
- 反过来也漏：明细表里有独立三级菜单「接收分组」，因为愿景表没突出它，整页漏建。

共同点：**做的时候都觉得很合理**。合理性不是判断标准，出处才是。

## 三、硬规则

在交付物第一节写明，并在整个过程中执行：

> 正文中的每一条功能需求都必须能在明细表中找到对应行号。凡是找不到出处的内容，一律归入「架构约束」或「待确认」，不混入正文。

三个合法去处，没有第四个：

1. **架构约束章** — 来自架构建议文档的内容，整章标注「非界面需求」
2. **待确认清单** — 明细表未定义或定义不完整之处
3. **调整建议** — 自己的判断，带理由与影响面，明确标注是建议

## 四、源冲突的处理

发现两份文档说法不同时，**采用明细表原文，并把冲突并列标出**。

```markdown
| 项 | 本版采用（明细表） | 另一文档 |
|---|---|---|
| 支付渠道 | 微信支付 / 支付宝（行 129，含 AppID/AppSecret） | FPS / 信用卡 / 银行转账 |
| 机构证件字段 | 统一社会信用代码（行 33/37/74） | 商业登记证 / 商业登记号 |
| 操作日志留存 | 保留最近 90 天（行 149） | 至少 7 年 |
```

然后给出判断，但把决定权交回去：

> 若服务对象为香港机构，港式口径（FPS / 商业登记号 / 7 年留存）可能更贴合实际，也更符合审计要求 —— 但这需要确认，不应由原型单方面决定。

**为什么不能默默改掉**：你确信更合理的那个选择，可能基于一个错误的项目背景假设。而且客户永远不知道自己被决定了什么——等到开发阶段才发现口径不对，返工成本远高于当场问一句。

## 五、缺口清单的写法

画原型会逼出大量源文档没写清的地方。这些是**一等交付物**，因为它们正是客户下次会议真正要讨论的东西。

### 按阻塞程度分三级

**P0 阻塞开发或影响数据模型**
- 状态机未定义（如「已支付」与「已完成」并存但无区别定义 → 收入统计口径和催缴范围都无法确定）
- 关键字段缺失（如履历没有「运动项目」字段，但档案库要求按项目筛选、统计、分卡片 → 三个功能全做不出来）
- 流程断点（如「后台续期为代操作」但后台没有续费入口）
- 账号无管理入口（如审核通过时自动建账号，但改密 / 禁用 / 交接都没地方做）

**P1 影响功能完整性**
- 入口缺失（三节点流程只实现了一节，前两节在任何端都找不到）
- 规则未定义（付费周期与到期日的计算关系、滞纳金的计息时点）
- 两侧结构不对称（一侧提交批次，另一侧按人审批，进度无法回显）

**P2 体验与细节**
- 示例格式与实际场景不符（脱敏示例用 11 位内地手机号，但服务对象用 8 位港号）
- 字段重叠（两个页面都有「名称」「Logo」，尺寸要求还不同）
- 孤立字段（某字段全文档仅出现一次，无获取规则、消耗场景、有效期定义）

### 每条要写清三要素

```markdown
| # | 事项 | 冲突/缺口 | 影响 |
|---|---|---|---|
| Q4 | 生涯履历缺少「运动项目」字段 | 添加履历（行 17）字段为类型/名称/时间/描述/附件，无运动项目；但档案库要求按项目筛选（行 46）、按项目统计（行 49）、按项目分卡片（行 53） | 三个功能无法实现，须补字段 |
```

**缺什么**、**在哪一行**（双向可查）、**影响什么**（决定优先级）。

### 编号与双向索引

给每条编号（Q1、Q2…），然后：

- 在缺口清单里给出完整描述
- 在各功能点正文里用 `⚠ 待确认：…（见 Q4）` 引用
- 在原型的「待确认」区域自动抽取这些 ⚠ 块并显示 Q 编号

构建后校验：正文引用的 Q 编号集合与清单定义的集合完全一致，不能有引用了未定义、或定义了没引用的。

```python
refs = set(re.findall(r'Q(\d+)', body))
defs = set(re.findall(r'\| Q(\d+) \|', todo_section))
assert refs == defs
```

## 六、被叫停后怎么处理

如果客户中途指出「你是不是多加了东西」，正确反应不是逐条辩解，而是：

**1. 立即核对，分类列清。** 五类分开列：整页自创的、页内溢出的、单方面改写的、编造数值的、以及**漏掉的**。漏掉的和多加的一样重要——只承认多加会显得在挑轻的说。

**2. 找根因并说出来。** 「我把三个 sheet 当一份文档合着用了」比「我疏忽了」有用得多——它让客户知道你已经定位了问题，而不是碰运气修。

**3. 给两个改法让客户选**，不要直接开始改：

- **严格收敛**：只留明细表列出的，超出的全删。适合给客户签需求范围。
- **分源标注**：保留但打标（愿景 / 架构建议 / 原型补充）。适合内部设计评审。

**4. 改完给出对照清单**，逐条说明删了什么、补了什么、以及哪几处源冲突现在改为并列标注等客户拍板。

最后这步不能省。改动本身需要被记录和验证，否则客户无法确认你到底改对了没有。原型里的「变更记录」区域就是为此存在的。
