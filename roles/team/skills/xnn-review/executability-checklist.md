# 可执行性审计清单

立场：视角审计员（可执行性）。标准只有一个：**开发拿到就能照着做，不需要再做任何设计决策。**

## X-NN 阶段：能不能拆

- [ ] 能拆成若干个可以独立提交、独立验证的改动
- [ ] 改动之间的依赖清楚，没有循环
- [ ] 每个设计决策都已裁决，没有“待定”
- [ ] 生命周期矩阵的每一格都能落到某个改动上，或已标“前端不提供”

## YY 阶段：逐个 YY 检查

- [ ] 一个 YY 对应一次独立提交，可以单独构建、单独验证
- [ ] 动作逐条列出，每条精确到：文件或模块、函数或接口、字段、配置、SQL 或迁移
- [ ] 接口：方法、路径、请求和响应字段、错误码
- [ ] 数据：表或字段的变更、迁移脚本、回滚方式
- [ ] 测试：要新增或修改的测试用例，覆盖正常、异常、边界情况
- [ ] 验证：执行哪些命令、看到什么结果算完成
- [ ] 写明前置 YY 和后续 YY
- [ ] 能回链到父 X-NN 的具体章节，以及对应的 PRD 条目
- [ ] 全文没有“待定”“视情况”“可选实现”“TBD”
- [ ] 逐个动作自问“还要不要再做选择”：只要有一处要选，这个 YY 就不合格
- [ ] 验证命令和手工冒烟，只用本 YY 及其前置 YY 已经交付的接口
- [ ] 测试断言里的计数（调用次数、事务数、行数）能由改动清单里的算法一步步推出来
- [ ] 每个新增的接口、错误码、配置项都能回链到 PRD 条目或闭环必检项；回链不上的属于“后置建议”，不应出现在 YY 里
- [ ] 粒度：改动清单超过约 8 项、或者同时混合基础设施和业务接口的，写了不拆的理由

**条件性 YY**：依赖还没交付的外部 X，单独计数，不算“可直接执行”。正文必须列出启动条件，以及开工前需要替换的推断名和未知项清单。

**代码未读时**：允许依据父文档“假设与裁决”里集中写的技术栈假设，把动作精确到 SQL 和函数，并在 YY 开头注明“未对照代码”。第一个 YY 的第一个动作必须是核对这条假设。“待定决策点为 0”在这种情况下指“除技术栈假设外为 0”。

## 输出

| 视角键（YY 或决策点） | 不合格项 | 出处 | 建议修法 | 候选修法数 |
|---|---|---|---|---|

最后附：每个 YY 的待定决策点计数（必须为 0 才算通过）。
