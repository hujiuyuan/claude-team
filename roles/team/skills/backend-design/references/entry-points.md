# 入口与生命周期

设计正文的**第一节**。讲不出入口，就等于没讲这段代码什么时候会跑。

## 一、入口六类

**入口的定义**：外部世界能触发本系统执行代码的那个点。

| 类型 | 是什么 | 典型样子 |
|---|---|---|
| HTTP | controller 方法 | 后台/官网的接口 |
| 定时任务 | 调度器触发的 job | cron 到点、手动补跑 |
| 消息 / 事件 | 消息队列消费者、发件箱派发器 | 异步解耦的那一头 |
| **回调** | 第三方打进来 | 支付网关回调、短信状态回执 |
| **入站远程调用** | 别人的服务调我方 | 内部服务间调用的被调方 |
| **启动期** | 应用启动时执行 | bean 注册、`@PostConstruct`、启动钩子 |

**回调必须单列**，不能混进 HTTP：它没有登录态、没有租户上下文、要验签、要幂等、要按对方要求的格式应答，生命周期跟普通 HTTP 完全不同。

**启动期最容易漏。** 症状是：接口定义得很漂亮，但全文没写谁在什么时候把它填满。典型例子——定义了一个"按 key 注册回调动作"的注册中心，却没写 register 在应用启动的哪个阶段被调、依赖哪些 bean 先就绪、注册失败应用起不起得来。

### 不是入口但要单独交代：出站远程调用

我方调别人，**不是入口**，是链路中间的一步。但它是整条链路上唯一一个"我方控制不了对端"的点，漏掉它失败分支就是假的。在链路图上单独标出，回答五问：

1. 超时多久
2. 重试几次
3. **重试是否幂等**（对端会不会因为重试多做一次）
4. 对端挂了，本方降级还是整条失败
5. 对端有没有限流 / 配额，打超了是排队还是直接失败（限流不是「挂了」，要单独回答）

## 二、十阶段统一骨架

**六类入口用同一套阶段，跑到同样深度。** 格子相同、答案不同，这才叫一致。

| # | 阶段 | 统一问句 |
|---|---|---|
| 1 | 触发 | 什么事件让这段代码开始跑？谁能触发？能不能重复触发？ |
| 2 | 准入 | 凭什么允许它跑？（白名单 / 登录态 / 权限点 / 验签 / 去重 / 条件装配） |
| 3 | **上下文建立** ★ | 租户从哪来？操作人是谁？跨租户怎么办？ |
| 4 | 入参解析与校验 | 输入长什么样、从哪解出来、非法输入怎么处理 |
| 5 | **幂等与并发控制** ★ | 同一份输入进来两次会怎样？上一轮没跑完这一轮又来了怎么办？ |
| 6 | 事务边界 | 谁开事务、传播行为、行级安全的租户值在哪设、批量时一条一事务还是整批一事务 |
| 7 | 业务执行与数据访问 | service 调用链、读写哪些表、owner 是谁、走哪个索引 |
| 8 | 提交后动作 | 提交后钩子、事件发布、发件箱落地 |
| 9 | **出口** ★ | 结果交给谁、交成什么形状、交错了对方会怎么反应 |
| 10 | **失败与留痕** ★ | 失败重试几次、耗尽落哪、审计写什么、脱敏 |

### 填写规则

- **带 ★ 的第 3、5、9、10 四格永远必答**——这四格跨入口类型差异最大，最容易照 HTTP 的直觉想当然
- 其余六格不适用时，**合并成一行**写掉（"本类无第 2、4、8 阶段，因为 X"），不逐格重复凑字数
- `S` 档只答四格；`M` 档十格全答但只对**新增/改动的入口**答；`L` 档全套

### 第 3 格是全局头号高危项

**六类入口只有 HTTP 天然带着可解析的上下文，另外五类全都没有。**
定时任务没有请求，回调没有登录态也没有可信的 Host 头，消息队列只有报文，启动期压根不属于任何租户。
启用了行级安全的表，不设租户值就查不到任何一行——**而且不报错**，表现是查不到，不是抛异常。这类 bug 上线后极难定位。

所以每类入口都要单独回答一次这一格，不许写"同上"。

## 三、完整范文：定时任务

证明这套骨架真能迁移，不是套模板。

| # | 定时任务的答案 |
|---|---|
| 1 触发 | cron 由调度中心配还是代码里写死；**时区基准写死哪个**；**多实例部署时会不会同时触发**；支不支持手动补跑；任务参数从哪传 |
| 2 准入 | 去重机制（单行标记表比较交换 / 分布式锁 / 调度中心自带）；能不能停用单个任务而不改代码重发版 |
| 3 上下文建立 ★ | **没有请求，租户值必须自己设**。两条路：遍历全部租户逐个设，或任务参数指定单租户。选哪条决定行级安全能不能生效；跨租户任务要不要换提权角色连库 |
| 4 入参解析与校验 | 分片序号、分片总数、执行参数怎么解；参数非法时是跳过还是报错停跑 |
| 5 幂等与并发控制 ★ | 上一轮没跑完这一轮到点了——串行等待、跳过本轮、还是并行跑；跑到一半进程挂了，重启后会不会把已处理的再处理一遍 |
| 6 事务边界 | 一条一事务还是整批一事务。整批：中间失败全回滚，一千条重来；一条一条：处理到第 500 条挂了怎么续上 |
| 7 业务执行与数据访问 | 批次查询走哪个索引；分页游标用主键还是时间（**用时间会漏掉同一时刻的多条**）；**过滤条件写宽了会误伤**——只该关"待支付"的单子，顺手放宽成"非已支付都关"就会关掉正在审核凭证的，而那些钱可能已经在路上 |
| 8 提交后动作 | 逐条处理里要不要发事件、落发件箱；整批跑完要不要汇总通知 |
| 9 出口 ★ | 执行结果怎么回报调度器（成功 / 失败 / 部分成功）；这次失败影不影响下次触发；执行日志留多久 |
| 10 失败与留痕 ★ | 单条失败是跳过继续还是整批中止；重试几次、间隔多少；重试耗尽落人工任务的哪一类；跑批留痕记什么（扫了几条、成功几条、耗时） |

### 另外五类的第 9 格（差异最大的一格）

| 入口 | 出口是什么 |
|---|---|
| HTTP | 响应体形状、错误码、多语言文案 |
| 消息 / 事件 | 确认还是拒绝；拒绝后重投几次；几次之后进死信；死信谁来捞；**同一实体的消息乱序了怎么办、积压的消费能力与告警阈值** |
| 回调 | **对方要什么格式的应答**——答错会被一直重推；验签之外防重放（时间戳窗口 + nonce 判重） |
| 入站远程调用 | 返回契约、超时语义、对方会不会重试 |
| 启动期 | 注册失败应用起不起得来 |

## 四、反查链

设计里新增的每个东西，都要能从入口反向追到。写成这个形状：

```
XxxUtil.foo()
  ← AaaServiceImpl.bar()
      ← AaaController.create()        [HTTP：有登录态、有租户、单条、请求内事务]
      ← BbbJob.run()                  [定时任务：无登录态、租户要自己设、批量]
      ← CccCallbackController.on()    [回调：无登录态、要幂等、可能重复进来]
```

### 多入口取交集：这是反查链真正的价值

**同一个方法被多个入口到达时，它的约束取所有入口里最严的那个。** 上面那个例子直接推出三条硬约束：

- 定时任务和回调没有请求上下文 → **租户必须显式传参，不许从线程本地变量里摸**
- 回调会重复进来 → **必须可重入，不能有一次性副作用**
- 定时任务是批量 → **自己不许开事务**，否则一批一千条开出一千个事务

这三条只写"这个工具方法干什么"绝对得不到。

### 效果一致：一个业务动作只能有一处实现

> **多个入口共用同一处实现，禁止按入口各写一份。**
> 判据：把任意一个入口整个删掉，业务动作的实现代码一行都不用改。

典型：入账这件事，线上回调、后台人工登记、线下凭证审核通过，三条路必须调同一个函数。各写一份的结果是三条路的行为在第三个月开始分叉，而且没人发现。

## 五、孤儿检查（强制卡口）

设计写完，新增的每个类、方法、表、枚举逐个过：

> **能不能从六类入口里的至少一个追到它？** 追不到的，要么漏了入口，要么它根本没人用——**补入口，或者删掉**。

反向警戒：**一次设计新增了一堆 service 和 DAO，却一个新入口都没有，一定有问题**——不是漏写入口，就是这批东西压根没人调。
