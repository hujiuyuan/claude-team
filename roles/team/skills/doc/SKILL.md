# 写文档

要写：$ARGUMENTS

所有文档都走这一个技能。先按下表判断类型，**只读对应的那一个要求文件**，不要全读；一篇文档只承担一种类型，混在一起时拆开写。

| 这次要写 | 读这一个 | 主要读者 |
|---|---|---|
| 技术方案 · 选型 · 重构评估 · 方案对比 | `types/design.md` | 我和开发 |
| 任务拆解 · 执行计划 · 排期 | `types/task-plan.md` | 执行的人或 AI |
| 需求分析 · 需求条目化 · 业务口径 | `types/requirement.md` | 设计者 |
| 建表 · 改表 · 字段 | `types/table.md` | 开发 |
| 功能设计 · 接口设计 | `types/api.md` | 开发 |
| 验收文件 · 验收用例 | `types/acceptance.md`（项目绑定字段见 `types/acceptance-binding.md`） | 验收者 |
| 周报 · 阶段工作汇报 | `types/weekly.md` | 领导 |
| README · 操作手册 · 概念说明 · 变更说明 | `types/readme.md` | 新人、使用者 |

判断不出类型时，按读者读完要做什么来选：要拍板 → 方案；要动手 → 任务拆解或接口；要验证 → 验收；要了解进展 → 周报；要上手 → README。

后端设计按「需求分析 → 表设计 → 接口设计」的顺序写，需求分析必须是成品（没有未决项）才往下走。

## 所有类型共用的规则

类型文件里的要求和这里冲突时，以类型文件为准。

1. **结论先行**：第一节就是结论或读者最需要的东西，不写铺垫。
2. **每条结论带证据**：文件路径 + 行号，或需求原件出处。查不到的标「未验证」或「我方预设」，不混在事实里。
3. **数量断言要么给查法，要么不写数字**：写「要改三处」就贴出得到这个数的命令。
4. **用具体数字代替形容词**；没有数据就不写数字。
5. **写当前状态，不写修改历史**：不挂「已定案」清单、不写「本文档结构说明」这类讲文档自己的章节。
6. **能放进表格某一格的事实就放进去**，不另起一段再补推导。
7. **命令和代码示例必须实际可运行**；没跑过的如实标「未跑」。
8. 改已有文档时保持原有结构和语气，只改需要改的地方。

## 交付前自查

```bash
grep -nE '为了更好|综上所述|总而言之|总的来说|接下来我们|下面我们|首先我们|值得注意的是|需要注意的是|值得一提的是|众所周知|本节将|在本节中|可以说|不难看出|非常重要|极其关键|至关重要|良好的|优雅|健壮|赋能|抓手' <文档>
```

命中即删。再按类型文件末尾的检查清单过一遍（有的话），清单本身不抄进产物。
