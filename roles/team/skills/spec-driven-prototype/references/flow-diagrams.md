# 流程图：泳道图与界面态交互流程

画流程时读。两种图解决不同问题，不要混用。

## 一、两种图的分工

| | 泳道流程图 | 界面态交互流程 |
|---|---|---|
| 回答 | 这件事经过哪些角色、谁在哪一步做什么 | 用户在这个页面上点了之后看到什么 |
| 节点 | 抽象方框（"创建会员档案"） | 真实界面缩略图 |
| 适用 | 跨端跨角色的业务主线 | 单页面的操作分支 |
| 数量 | 每条业务主线一张 | 每个页面一份 |

业务主线用泳道图（谁做的），页面交互用界面态图（看到什么）。用泳道图画单页交互会丢掉「错误提示长什么样」，用界面态图画跨端流程会画不下。

## 二、泳道流程图

竖向泳道（列＝角色），流程自上而下。比横向泳道更适合中文场景——角色名短、步骤多。

```js
{lanes:['申请人','前台系统','后台','系统自动'],
 nodes:[
   {id:'s',  l:0, r:0,  k:'t', t:'开始'},              // l=泳道 r=行
   {id:'fill',l:0, r:2, no:'2', t:['填写并提交申请','会员类型 / 证件号']},
   {id:'d1', l:2, r:7,  k:'d', t:'审核通过？'},
   {id:'bind',l:3,r:19, k:'key', t:['★ 账号 ↔ 档案','自动绑定']}
 ],
 edges:[
   {f:'d1', t:'rej', r:'v', lb:'否'},                  // 同泳道垂直
   {f:'d1', t:'arch', r:'r', lb:'是'},                 // 从右侧出，跨泳道
   {f:'rej',t:'fill', r:'b', cx:16, side:'l', tside:'l', lb:'修改后重提', dash:1}
 ]}
```

五种连线路由：

- `v` 同泳道垂直向下
- `e` 跨泳道折线（下 → 横 → 下）
- `r` / `l` 从菱形侧面出，横穿到目标泳道再下
- `b` 回流线：侧面出 → 走左侧通道 → 向上 → 进目标侧面（配 `dash:1` 画虚线）

**判断节点的两条分支不要都从底部出。** 「否」走底部垂直、「是」从右侧出，否则两条线重叠在同一个点上很难看。

**节点编号很有用。** 给每个节点标 `no:'7'`，正文注释里就能写「关键节点 7：账号在这里交接」，图文可以互相引用。

**用 `k:'key'` 高亮关键差异节点。** 例如三条入会路径里，只有一条会自动绑定账号——把那个节点做成实心高亮，一眼能看出三条路径的本质区别在哪。

## 三、界面态交互流程

参考模式：左侧字段注释（虚线引导）→ 默认态 → 提交中 → 判断链（横向）→ 各错误态（上下分布）→ 成功终态。

### 界面态素材库

不要用方框代替界面。做一套缩小版真 UI：

```js
const U = {
  ttl:  t => ({h:26, html:'<div class="uipt">'+t+'</div>'}),
  filt: l => ({h:32, html:/* 筛选条 chips */}),
  tbl:  (c,n) => ({h:26+n*19, html:/* 表头 + n 行占位条 */}),
  emp:  t => ({h:66, html:/* 空态 */}),
  fld:  l => ({h:l.length*33, html:/* 表单字段行 */}),
  ban:  (t,k) => ({h:32, html:/* 红/绿提示条 */}),
  btn:  (t,k) => ({h:34, html:/* 按钮，k='load' 带转圈 */}),
  skel: n => ({h:n*17, html:/* 骨架屏 */}),
  // 还需要 kv / tabs / tree / chart / kpi / qr / bar
};
```

每个函数返回 `{h, html}`——`h` 供布局引擎算坐标。这是关键：布局要精确就必须知道每块内容的高度。

界面态由素材组合而成：

```js
S('② 空态', [U.ttl('会员列表'), U.filt([...]), U.emp('调整筛选条件后重试')], {err:1})
```

### 自动布局

页面数量一多，手写坐标不可行。用「流程带」结构自动排：

```js
uif({
  notes: [{title:'账号输入框', items:['输入后显示清除图标','最多 100 字符']}],
  chains: [
    {lb:'主流程 · 进入页面',
     n: [S('① 加载中',...), D(['是否有数据']), S('③ 列表态',...)],
     b: [{at:1, dir:'up', lb:'N｜无数据', node:S('② 空态',...)}]}
  ]
})
```

引擎负责：注释列堆叠 → 每条流程带占一个水平带 → 带内节点横向排列 → 分支节点放在带的上方或下方 → 计算画布尺寸。

`at` 指分支挂在链上第几个节点（索引），`dir` 是 `up` 还是 `down`。上下分开放能避免同一个判断的两条分支重叠。

### 字段注释的引导线

注释框在左侧一列，虚线指向界面上对应的字段。因为字段间距只有 32px 而注释框高 120px+，无法一一对齐，所以用折线：

```
M(注释框左边, 注释框中心y) H(通道x) V(目标字段y) H(界面右边)
```

给每条引导线不同的通道 x（如 302 / 308 / 314）避免竖段重叠。目标字段 y 需要手工估算——从界面态卡片顶部往下累加各素材高度。

### 页面原型模板

59 个页面手画不可能。**大部分页面的交互骨架本来就是同一套**：

| 模板 | 生成的流程 |
|---|---|
| 列表型 | 加载 → 有无数据 → 列表态 / 筛选 → 命中与否 / 导出 → 空数据拦截 |
| 详情型 | 加载 → 只读态 / 点编辑 → 编辑态 → 校验 → 保存成功 |
| 审核型 | 列表 / 通过 → 确认框 → 系统动作链 / 驳回 → 必填原因 → 校验 → 通知 |
| 表单型 | 空表单 → 前端校验 → 提交中 → 服务端校验 → 成功（两处失败分支） |
| 配置型 | 配置态 / 编辑弹窗 → 校验 → 生效提示 |
| 树形型 | 树只读 / 新增节点 / 删除节点（级联确认） |

模板不是偷懒。硬把结构相同的页面画成 60 个不同的图只会制造噪音。差异化的部分用参数传进去：各页真实的字段、筛选项、弹窗内容、系统动作说明、以及各自的待确认项。

真正需要手写的是交互确实特殊的那些——通常占 15%~20%。判断标准：**这个页面的分支逻辑能不能被上面六个模板中的一个完整表达**。不能的才手写。例如：

- 双栏选定 + 相似度提示 + 不可逆二次确认（档案合并）
- 提交前本地查重 + 打回后就地重提（批量推荐）
- 骨架屏 → 接口异常降级 → 视口分支（官网首页）

## 四、画流程会逼出的缺口

这是画图最大的副产品：**流程末端画不下去的地方，就是需求没写清的地方**。

例：催缴管理页画到「勾选订单 → 选模板 → 预览 → 发送」之后就断了——因为「订单多久转已过期、过期后会籍怎么办」没定义。这个断点在文字需求里看不出来，画图时立刻暴露。

再例：订单详情页的「变更状态」链缺一个节点——官网允许会员上传线下转账凭证，但后台没有凭证查看界面，财务点【变更状态】时看不到凭证。图上这一步是空的。

把这些断点就地标在图旁的注释里，并关联缺口清单的编号。

## 五、几何自检

自动布局必须程序化验证：

```js
// 包围盒重叠
for (let i=0;i<nodes.length;i++) for (let j=i+1;j<nodes.length;j++) {
  const ox = Math.min(a.x+a.w, c.x+c.w) - Math.max(a.x, c.x);
  const oy = Math.min(a.y+a.h, c.y+c.h) - Math.max(a.y, c.y);
  if (ox>2 && oy>2) report('重叠', a.id, c.id);
}
// 越界 / 连线端点有效 / 孤立节点 / SVG 中出现 NaN
```

`NaN` 检查特别重要——某个节点没给 `h`，中心点算出 `NaN`，整条 path 静默失效，视觉上就是「少了一根线」，很难注意到。
