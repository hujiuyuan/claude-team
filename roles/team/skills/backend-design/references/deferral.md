# 主线 / 支线 · 阻碍分级 · 候补

产品经常没完全想清楚。这时候逼他现在拍板，逼出来的答案质量比候补还差。**支线上条件不满足的事，问的是"能不能候补"，不是"选哪个"。**

## 一、主线三问

**主线 = 从入口到这个功能的价值兑现，那条最短的完整链路。**

三问，任一命中即主线：

1. 去掉它，主流程还能从入口跑到终点吗？——**不能** → 主线
2. 去掉它，**本次功能自己产生的**数据会不会错、丢、对不上账？——**会** → 主线
3. 去掉它，**本次功能自己**会不会留下钱、权限、合规的敞口？——**有** → 主线

### 两条防滥用规则（不加就一切都成主线）

**第 2、3 问必须点名具体项**：第 2 问点名是哪条数据会对不上，第 3 问点名是什么风险、谁受损。
**点不出具体的，一律判支线。** 「有合规风险」「数据可能有问题」这种泛泛之词不算命中。

**粒度必须拆到任务级，不能按模块判。** 同一个功能里主线支线都有。
举例——某笔钱在订单已关闭之后才到账：
- "这笔钱要不要入账" → **主线**（第 2 问命中，点得出：不入账则流水与银行对不上）
- "给财务看的人工处理界面" → **支线**（流程跑得通，钱已入账，只是没人管得漂亮）

按模块判会把这两件事一起判成主线，然后为了一个界面卡住整条线。

## 二、阻碍五级

| 级 | 是什么 | 处置 |
|---|---|---|
| 🔴 **主线阻塞** | 主线上，不定就写不了第一行代码 | **停下来问，必须现在定** |
| 🟣 **支线待定** | 支线上，条件不满足 | **问能不能候补**，带五要素提案 |
| 🟠 **形状对不上** | 下游已写好但对不上，要返工 | 不问，直接定处置 |
| 🟡 **等外部件** | 逐条核实真在等还是假在等 | 只留真的 |
| ⚪ **口径陷阱** | 不阻塞但写的时候会踩 | 进坑清单，挂到具体任务上 |

### 判错的代价（强制）

**每条判为非 🔴 的阻碍，必须多写一行：**

> **判错的代价**：如果这条其实必须拍板而我自作主张定了，最坏会怎样。

写不出代价的，说明没想清楚，降不了级，退回 🔴。
这一行同时是给人复核用的——扫一眼所有「判错的代价」，就能挑出误判的那条。

🟣 的这一行特化成：**如果它其实在主线上而我判成了支线，代价是什么。**

### 🟡 要真的核实

"等别人给假件"这类事项最容易虚报。逐条去代码里验：
- 说等迁移号段的 → 去看各分支的最高迁移号，空号段够不够
- 说等起环境脚本的 → 去看种子数据文件在不在、能不能重复执行
- 说等某个校验的 → 去看它依赖的数据模型有没有建

核完往往只剩一两条是真的在等。**真在等的那条，还要区分"等一个假件"还是"等一整块数据模型"**——后者严重得多。

## 三、"产品没想清楚"的识别信号

在 PRD 取证阶段就要认出来。命中任一信号，**默认走 🟣 候补路线，不逼产品现在拍板**：

- PRD 里自称「暂定 / 待定 / 后续优化 / 一期先不做」
- **原型或需求文档里专门标未定项的那一段**（有些原型有 `todo` 字段，逐个扫）
- 同一件事 PRD 两处写得不一样，而且**两处都很含糊**——这是没想清楚，不是硬冲突；硬冲突走改判
- 只画了正常路径，异常和边界一个字没写

## 四、候补提案五要素

问"能不能候补"时必须带齐，让候补这个选项好选：

| # | 要素 | 要求 |
|---|---|---|
| 1 | **它是什么** | 一句话 |
| 2 | **为什么现在做不了** | 条件不满足的具体原因 |
| 3 | **不做的影响面** | 哪些场景没人管、用户会看到什么 |
| 4 | **候补的代价** | 现在留什么接缝 / 以后补时要改哪些地方 / **可不可逆** |
| 5 | **我的建议** | 候补 / 现在必须定，二选一 |

### 可逆性要单独标红

有些东西候补了以后补不回来：
- 数据当时没采集（历史数据无法回溯生成）
- 编号已经发出去了（改格式会让已发出的失效）
- 外部系统已经按旧形状集成了（改了要对方配合）
- 存量数据已按旧口径落库（要写数据订正脚本）

**不可逆的候补必须标红警告**，不能混在普通候补里被顺手批准。

## 五、候补三处落地，缺一不可

光写 `// TODO` 一定会烂在代码里。

### 1. 代码里留接缝，不是留注释

**接缝 = 一个只有一处实现的接口或方法，带类注释写明它是临时状态。**

```java
public interface XxxGuard {
    /** 判定 ...。数据模型未落地前恒返回放行 */
    Verdict check(...);
}
```

类注释里必须写明：**「恒放行是临时状态，X 落地前不要当成业务规则」**。

接缝比 `// TODO` 强一个量级：
- 有真实调用点（不是飘在注释里）
- 有类型签名（编译器帮着守）
- 删不掉（删了编译不过）
- 以后换实现时**调用方一行不改**

**区分清楚**：接缝是给自己留的调用位置，**不是替别人编假件**。别人负责的数据模型或接口形状，不许自己编一个假的顶上——那会让两边在第一天就长歪。

### 2. 未决台账

独立一份文件，跨轮次累积。每条记：

| 字段 | 内容 |
|---|---|
| 编号 | 台账内递增，跨文档引用的锚点 |
| **登记轮次与基线** | 第 N 轮 · PRD 的 sha256 前 8 位。**台账是唯一跨轮次累积的产物，指纹记在每一条上，不记在文件头**——多轮混在一份里，头部记单一指纹说明不了任何一条是在哪个版本下判的，而基线一变，那条的「恢复条件」可能早就失效了 |
| 状态 | `待拍板` / `已候补` / `待外部需求方答复` |
| 是什么 | 一句话 |
| 为什么候补 | 条件不满足的原因 |
| 谁拍的板、哪天 | 有名有姓有日期 |
| 接缝在哪 | 文件路径 + 类名/方法名 |
| 恢复条件 | **什么条件满足了就能做**——写不出恢复条件的候补等于永久搁置 |
| 可逆性 | 可逆 / ⚠️ 不可逆 + 为什么 |

台账吸收了三类原本会散开的东西：设计文档的「待拍板汇总」、给外部需求方的澄清清单、候补项。**同一件未决的事只有一处正文**，设计文档里只留编号索引。

### 3. 设计文档留指针

正文里该讲它的地方写一行指回台账编号，**不复述内容**（复述就是两份漂移）。

### 机器兜底

校验脚本对账两条：
- 代码接缝注释里写的台账编号，必须在台账文件里存在
- 台账里每条记的接缝路径，必须在代码里存在

两边对不上就报错。这样候补项烂不掉。

## 六、给外部需求方的澄清（台账的一个视图）

问题要转给外部需求方（客户、产品、法务）时，从台账里筛出 `待外部需求方答复` 的条目，导成一份能脱离上下文单独读懂的文件。要保留四层意思：

1. 每条都给了「建议默认」，只需**确认或否决**，不必从零设计
2. **超过回复日期未答复的，开发按建议默认实现**
3. 每条都标了出处，方便核对
4. 按紧急度分三组

紧急度按**谁该答 / 答不出的后果**分，不按改动成本排：

| 组 | 判据 | 标记 |
|---|---|---|
| A | 不答无法开工 | 🔴 阻塞 |
| B | 影响本期范围与工期 | 🟡 影响工期 |
| C | 源文档内部打架，需求方自己对齐即可 | 🟢 对齐 |

每条的「不答的后果」**量化到人日或周**（"写死 3–5 天 vs 做成配置 3–4 周"），不写"高/中/低"。
用业务语言写，不出现字段名和技术方案。
